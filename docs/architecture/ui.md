# Interface components

Kisa's interface behavior comes from [ui-sdk](https://ui-sdk.dev): keyboard navigation, focus, selection, dismissal, popups, drag and drop, and the ARIA they need. ui-sdk renders no styles of its own; Kisa styles it with Tailwind and the design tokens in `assets/main.css`. Kisa does not load ui-sdk's optional `web.css`.

The docs for the installed version ship with the package. Read `apps/desktop/node_modules/@ui-sdk/react/docs/llms.txt` first, then only the component pages a change needs, such as `docs/components/menu.md`. `docs/core.md` covers building components from behaviors; it is over 300 KB, so search it by heading. The `.d.ts` files are the API; never read the compiled `dist/*.js`.

## Layers

```text
feature component ──> @/components/ui/<name>  (Kisa's styled wrappers)
                 │          └──> @ui-sdk/react/<name>
                 └──> @/primitives/<name>     (Kisa's own primitives)
                            └──> @ui-sdk/core behaviors + @ui-sdk/react/primitive
```

- `renderer/src/components/ui` holds Kisa's styled wrappers. Each wraps one ui-sdk component, keeps ui-sdk's part names, and adds only classes and Kisa defaults. Feature code imports components from here, not from `@ui-sdk/react` directly, so the look stays in one place.
- `renderer/src/primitives` holds behavior ui-sdk does not ship, written with `definePrimitive` from `@ui-sdk/core` behaviors and rendered with `createParts` from `@ui-sdk/react/primitive`. Each primitive declares the ARIA pattern it follows, its keys, and its `agent.actions`, and has tests that use `mount` and `checkPattern` from `@ui-sdk/core/testing`; `checkPattern` knows no window splitter, sortable list or grid, so `splitter` (the sidebar's resize handle), `sortable-list` (the account order) and `mail-list` (the mailbox, search results and Scheduled; see [mail-list.md](mail-list.md)) are tested key by key. `sortable-list` and `mail-list` key their items with the `"string"` prop kind: with `"key"`, React parts threw "reading 'keyOf'" on render in 0.1.0-beta.16.
- A primitive that renders a list from data, like `mail-list`, has a root written with `usePrimitive` and `usePart` (`MailListRoot`), which reads the virtualizer's rows with `useSyncExternalStore`; its row parts come from `createParts`. Feature code drives it from outside through a controller from `createController`, passed as its `controller` option, and keeps the app's state the source of truth through the `on<Key>Change` callbacks.
- Layout-only pieces without behavior, such as `Empty`, `Item`, `Kbd` and the settings rows, use `renderElement` and `mergeProps` from `@ui-sdk/react/primitive` so they accept the same `render` prop as every other part. Settings rows sit in a bordered card (`settingsRowsClassName`, also used by the AI provider radio group) under an `h3` section title, since the Settings dialog's title is the `h2`.

Before writing a `role=` attribute or a key handler for a widget, look for the component in the docs' component list or a behavior in Core's "All Behaviors". A `div` with `role="listbox"`, `"menu"`, `"dialog"`, `"tablist"`, `"separator"`, `"switch"`, `"slider"`, `"radiogroup"`, `"toolbar"` or `"tree"` is almost always a bug.

## Styling

- State variants (`data-open:`, `data-checked:`, `data-selected:`, `data-disabled:`…) come from `assets/utilities.css`: they match an attribute that is present unless its value is `"false"`, so they work for ui-sdk's presence attributes and for React booleans alike. The same file holds the `scroll-fade-x`, `scroll-fade-y` and `no-scrollbar` utilities.
- `@layer ui-sdk;` is the first line of `assets/main.css`, so Tailwind's layers win over the little CSS ui-sdk adds at runtime. Every window imports that stylesheet. All three windows' Content Security Policies allow `style-src 'unsafe-inline'`, which ui-sdk's runtime styles need.
- Style state from attributes: `data-open`, `data-closed`, `data-highlighted`, `data-checked`, `data-pressed`, `data-disabled`, `data-pending`, `data-side`, and the rest each component page lists. A part's `data-slot` is set by ui-sdk; wrappers don't set it.
- Animate popups with transitions from `data-starting-style` and to `data-ending-style`. ui-sdk keeps content mounted until its exit transition finishes. Don't animate presence with keyframes; for an element that appears from `hidden`, Tailwind's `starting:` variant (`@starting-style`) gives the entry transition. The `.reduce-animations` class on `<html>` turns every transition off, and ui-sdk then closes at once.
- A popup animates once, through its wrapper's transition (opacity and scale, 100 ms), and nothing else. Don't add transitions, Motion, or `starting:` styles to its content. Don't unmount the content yourself (`{open ? <PopoverContent /> : null}`) or change its `key` when it closes: either cuts the exit short or swaps the content while it fades. ui-sdk unmounts closed content after the exit, so each opening starts fresh. A component that holds its state outside the content, like the Pick date and time dialog, stays mounted and changes its `key` when it opens.
- Menus have no transition on purpose: a menu item often opens a dialog, and a menu fading out would overlap the dialog fading in.
- The sidebar's disclosures, an account's mailboxes and its Labels, open in a `SidebarDisclosurePanel`: its height moves from and to zero with `--collapsible-panel-height`, over the 150 ms the chevron takes to turn. The panel clips while it moves, so it reaches 2px past its rows on every side to keep their focus rings whole. The conversation's messages and a forwarded message open at once: their bodies are iframes that size themselves after they load, so the height measured on opening is wrong, and opening a message also scrolls to it.
- Progress rings ease between readings over 300 ms, as the update button's ring does. ui-sdk writes a `Progress` root's value to `--progress-value`, which `main.css` registers as an inherited `<percentage>` so it can transition, and Kisa's `Progress` transitions it.
- Moving an account slides the account rows to their new places: each `SortableListItem` renders an `m.li` with `layout="position"`, and `layoutDependency` set to its place in the order, so nothing else that shifts a row, like a panel opening above it, slides it. The row being dragged doesn't animate: it follows the pointer through ui-sdk's `--drag-y` only, so it stays in the list's column, on the sidebar's background so the rows it passes don't show through.
- Something that appears from nothing eases in with `starting:` styles: Add account's notices under the form fade and rise 4px over 150 ms, its steps fade in 8px from the side they come from (the form from the end, the provider list from the start when going back, and nothing when the window opens), and the conversation's loading screen fades in only after 200 ms, so a conversation the cache answers for never flashes it. Lines that change as someone types, like Add account's own problem line, appear at once. A draft's attachment pills enter and leave as the draft history's do, with Motion's `popLayout`.
- A press on a tooltip's trigger closes the tooltip at once (`data-closes-at-once`), so it never animates over the popup the press opens. A tooltip closed any other way fades out.
- Popovers, menus, selects, tooltips and dialogs render in place in the browser's top layer. There is no Portal or Positioner part, and they need no `z-index`. ui-sdk positions anchored content (popover, menu, select, tooltip) with inline styles, so don't add `fixed`, `absolute`, `top` or `left` to it. Dialog content and its backdrop are not anchored: ui-sdk resets their popover styles, and the wrapper positions them.
- The window itself never scrolls: the shell's root is `relative overflow-hidden`, and its `<main>` scroll area is `relative`. ui-sdk's form controls (Switch, Radio, File Input) render a visually hidden native input positioned absolutely; inside an unpositioned scroll area it would escape to the page and give the window a second scrollbar. A new scroll area that can hold such controls is `relative` too.
- A class that sets `display` on popup content overrides the browser's rule that hides a closed popover, leaving only `hidden` to hide it, and ui-sdk writes `hidden` a render after the popover closes. Until then the content is a `fixed` box outside the top layer, placed against the nearest ancestor with a `transform`, `translate`, `filter` or `backdrop-filter` instead of the window. `TooltipContent` carries `not-open:hidden` for this, since tooltip content stays in the page.
- A floating bar that holds popup triggers sits in a positioned `overflow-clip` box, as the mailbox's selection bar does in `thread-list.tsx`: clipped but not a scroll container, so nothing the bar holds can lengthen the scrolling `<main>`. The top layer is not clipped.
- A dialog's actions go in `DialogFooter` or `AlertDialogFooter`, which share one layout (`dialogFooterClassName`): a row at the trailing edge, inside the dialog's padding, at every window width, with Cancel as a `secondary` button before the action. A dialog passes its footer no layout classes and its buttons no size. Don't pull a footer out to the dialog's edges: a footer flush with a rounded dialog has to clip its buttons, which also clips their focus rings, and a destructive question opens with the keyboard on Cancel.
- Wrappers take `className` as a string and merge it with `cn`. A wrapper that appends its own children, like `DialogContent`'s close button, takes `children` as nodes, not as a function of state.

## Behavior to keep in mind

- `onOpenChange(open, details)`, `onValueChange(value, details)` and the other change callbacks report `details.reason` (`trigger-press`, `outside-press`, `escape-key`, `close-press`, `item-press`…), `details.source` (`keyboard`, `mouse`, `agent`…), and `details.cancel()` to refuse the change. Keep app state in sync through these callbacks, not DOM listeners.
- A `Button` whose `onClick` returns a Promise stays pending until it settles: it ignores presses, gets `data-pending` and `aria-busy`, and keeps focus. Return the Promise when a double press would repeat a remote action.
- `initialFocus` and `finalFocus` take an element, a selector, or a function: pass `() => ref.current`, not a ref object.
- Your event handler on a part runs before the part's own. `event.preventDefault()` skips the part's handler.
- Tooltip content is in the page from the first render, hidden, so it can name an icon-only trigger. Server-rendered markup in tests contains it. Kisa's `Tooltip` opens without a delay, and closes before an Escape reaches anything else so the key still runs the app's command; tooltips group without a provider.
- `Spinner` is hidden from assistive technology unless it gets an `aria-label`, which makes it a `role="status"`. Name it only when nothing nearby already says what is loading.
- A decorative `Avatar` beside a visible name takes `aria-hidden="true"`; otherwise the agent bridge lists it as an unnamed image.
- Keyboard shortcuts go through `@/hotkeys` (see [hotkeys.md](hotkeys.md)), which registers them in ui-sdk's shared `shortcuts`. Don't give ui-sdk triggers a `shortcut` prop or call `useShortcut` or `registerShortcut` from feature code. A widget that `preventDefault`s a key keeps it from every command, so a widget that should let a chord like `Mod+Enter` through leaves it unprevented.
- A menu opened by setting its `open` prop leaves focus where it was. A shortcut that opens a menu, like Mod+L for labels or Mod+Shift+Enter for Schedule send, calls `menu.open({ focus: "first" })` on a controller from `createMenuController()`. Popovers and dialogs opened through `open` do move focus to their `initialFocus`.
- Menu items run `onSelect`, for the pointer and Enter alike. `onClick` misses Enter.
- Text fields sit inside a `Field` with a `FieldLabel`; mark a field invalid with the Field's `invalid` prop. `FieldError` renders only inside a Field, so a form-wide message is a plain `role="alert"` element. A control that isn't a ui-sdk part, like a button that opens a date popover, takes a `Label` with `htmlFor` instead of a `FieldLabel`.
- An input with addons is an `Input` inside `InputGroup`; the group draws the focus ring and border, and `InputGroupAddon` holds icons and buttons.
- Kisa's `Popover` refuses the `window-blur` dismissal, so switching to another window keeps a popover and what was typed into it.
- A Trigger Menu on a Tiptap editor connects through `useTiptapTriggerMenu` from `@/editor/use-tiptap-trigger-menu`. Unlike other popups, a trigger menu's layer sees Escape only after `@/hotkeys` does, so the hook closes the menu from the editor's key handling and marks the key handled, which every command skips.
- ui-sdk's Command clears its search on a first Escape and has no option to close instead. Kisa's `CommandInput` takes `onEscape`, which runs on that first Escape in place of the clear (and not while an IME is composing), so the search bar and the stash and variable pickers close at once.
- A Combobox whose options load as someone types controls `open`, so an empty popup never shows, and also passes those options as `items`, so an agent's `setValue` doesn't wait for the list to open.
- `useConfirm()` asks through ui-sdk's `createConfirm`: questions wait their turn, focus returns to where it was, and the confirming button's `data-agent-confirm` repeats the question's title and description. Return and Space press the focused button. A destructive question (`confirmVariant: "destructive"`) opens on Cancel, so a reflexive Return answers no; any other question opens on its confirming button; a typed confirmation opens in its field, where Return confirms once the text matches.

## Agents and privacy

Every control has an accessible name: a label part, a title, or `aria-label` on an icon-only control. Names a person would use double as the names ui-sdk's agent bridge finds controls by. Actions that send mail, delete it, or disconnect an account carry `data-agent-confirm` with a sentence describing the effect. Kisa does not create an agent bridge or register WebMCP tools in the app, because that would expose the mailbox to page-level automation; `createAgent` appears only in tests.

- The bridge lists only ui-sdk parts, so every control is one: a Kisa `Button`, never a plain `<button>`, even one restyled to look like text or a badge. Override the look with classes (`h-auto`, `p-0`, `border-0`, `text-[length:inherit]`, `active:not-aria-[haspopup]:translate-y-0`) rather than leaving the button bare.
- Render a menu, popover or dialog trigger as `<MenuTrigger render={<Button … />} />`. Kisa's `Button` sees the trigger's `aria-haspopup` and renders a plain styled `<button>`, so the bridge lists the control once, as the popup, not also as a button. A Kisa `Button` with `aria-haspopup` of its own is likewise left to its popup's entry.
- A button that stays pressed until pressed again is a `Toggle`, never a `Button` with `aria-pressed`: the bridge lists a `Button` as a plain button and drops the pressed state, while a `Toggle` reports it and takes `setPressed`. `variant` sets the unpressed look and `pressedVariant` the pressed one (`ghost` keeps the unpressed look). One choice among several that always holds one, like the From account, is a `ToggleGroup` with `deselectable={false}`: one tab stop, the arrows move focus, and a press chooses, where a Radio group would choose on every arrow. A popup trigger is never pressed, since it already reports its popup; its name carries the state instead ("Edit link", "Selected send time: …"). An action that only looks like a state, like rolling a random label color, is a plain `Button`, disabled when there is nothing to do.
- A control that shows and hides content is a `Collapsible` from `@/components/ui/collapsible`, whose `CollapsibleTrigger` is styled like a `Button` and takes the same `variant` and `size`. Don't write `<CollapsibleTrigger render={<Button … />} />`: the bridge would list the control twice, as a button and as the collapsible. A sidebar row that discloses, like Labels, takes `SidebarRow`'s `disclosure` prop for the same reason. The panel unmounts while closed.
- Pages that share one space, like the Settings dialog's, are `Tabs` from `@/components/ui/tabs`, vertical there. A tablist holds only tabs, so the Accounts heading among them is `aria-hidden` and each account's tab names itself by its address. The bridge lists the tablist ("Sections") as one control with `setValue`, whose values are the page ids (`general`, `ai`, `data`, `account:<address>`); a step that names a control on another page fails with a list of the pages it might be behind. Settings' search is a `Command` ("Search settings") with `filter={false}`, since `settings-search.ts` ranks the results, and `autoHighlight`, so Enter takes the best one; a result names its setting and then its page, so two accounts' signatures differ. Its list stays mounted, `hidden`, while the search is empty, and the pages' tablist is hidden while it isn't, so neither tab nor result unmounts under its controller. A row a result leads to is a `SearchableSettingsRow`, whose `data-search-highlighted` tints it.
- Sections that open and close in place, like a conversation's messages, are an `Accordion` from `@/components/ui/accordion`, whose `AccordionTrigger` is styled like a `Button` for the same reason. Each trigger sits in an `AccordionHeader` rendered as an `h2`, under the subject's `h1`, so screen readers can move between messages by heading. The bridge lists the accordion as one control, named by its `aria-label` ("Messages"), with its items; an agent opens an item by its value, the message id, not by its label. A conversation's accordion is `multiple`, so several messages can be open at once. The conversation store stays the source of truth: the accordion's `value` is the set of open messages, and a press runs the store's toggle on the message it opened or closed, which also selects that message. A press anywhere in an open message's body, attachments, or notices selects it too, without opening or closing it; the sender's document reports its presses through a listener the body attaches to it, since its events never reach the app's.
- Files come in through a `FileInput` from `@/components/ui/file-input`, never a hidden `<input type="file">`. Where the app keeps its own list, like a draft's attachments that main authorizes, the `FileInput` holds nothing (`value` stays empty) and hands `details.added` on from `onValueChange`; a shortcut opens its picker through a `createFileInputController()` controller's `open()`. Its `FileInputTrigger` is styled like a `Button` for the same reason as the triggers above. A `FileInputDropzone` claims every drop inside it before its children see one, so it never wraps something that takes its own drops: the new-email page keeps its own drop handling, which leaves drops over the message editor to the editor.
- A color is a `ColorPicker` from `@/components/ui/color-picker`, which the agent bridge lists as one `color-picker` with `setValue`. A label's color picker holds `#rrggbb` written in hex: its area, hue slider, hex input and eyedropper sit in a `Popover` whose trigger shows the swatch (the eyedropper hides itself, `data-unsupported`, where the browser can't pick from the screen), and it cancels a change that isn't an opaque `#rrggbb`, like a typed color with alpha. The popover has no title, so its content and trigger both carry `aria-label="Pick color"`, a name apart from the picker's "Label color". ui-sdk puts a thumb's top-left corner on its point; Kisa's thumbs center themselves with `-translate-x-1/2 -translate-y-1/2` (an arbitrary `translate-[-50%_-50%]` does not compile to a translate in Tailwind v4).
- A time of day is Kisa's `TimeInput` in a `Field`. With no `lang` on the page, it shows the clock of the system's language, as Kisa's other times do; its value is `"HH:MM"` or `null` while partly typed, and the Field's `invalid` reaches it. Enter in it submits its form, so it sits in a `<form>` whose submit button runs the action, rather than behind an Enter handler.
- A date is Kisa's `DatePicker` in a `Field`, holding `DatePickerInput`, `DatePickerTrigger` and `DatePickerContent`, which draws the month itself. Its value is an ISO date (`"2026-11-20"`) or `null`, typed in the system language's date order or chosen from the calendar. `min` refuses an earlier day whether it's typed, chosen or set by an agent, and text that isn't an allowed date keeps its form from submitting, so the form's own checks never see it. Like Kisa's `Popover`, its calendar refuses the `window-blur` dismissal. A day chosen in the calendar (`details.reason === "item-press"`) can send focus on through the content's `finalFocus`, as Pick date and time sends it to the time.
- A disabled control with a tooltip keeps `focusableWhenDisabled` (on `Button` and Kisa's `Toggle`): it uses `aria-disabled` instead of the native attribute, so keyboard users can reach it and read the tooltip, and ui-sdk's strict mode rejects a natively disabled tooltip trigger. Only a natively disabled button drops pointer events. Kisa's `hover:` variant never matches a `data-disabled` element, so a focusable disabled control shows its tooltip on hover without looking pressable. Don't wrap a disabled button in a span to give its tooltip a target.
- Put `disabled` on the trigger part, not on the `Button` inside it. A disabled trigger refuses an agent's `press` but not its `setOpen`, so a popup that must stay shut while disabled cancels opening in `onOpenChange` (`if (open && disabled) details.cancel()`).
- A `Tooltip` around a popup trigger shares the trigger's name, and the bridge still matches it while it's closed. Put `data-agent-hidden` on its `TooltipContent`. A tooltip around a plain `Button` needs nothing.
- A step's name matches every label that holds its words, so controls on one surface each need a word of their own: "Send email" beside "Schedule send", "Sync now for ana@example.com" in each account's section. Repeated rows name their row: "Edit Travel for ana@example.com", "Edit Reply instructions".
- A `useConfirm` action leaves its trigger unmarked: the dialog's confirming button already carries the question, and marking both asks twice. Give the confirming button text the trigger's name lacks ("Delete forever" for "Delete template"), and the title a word the trigger lacks ("Disconnect account?" for "Disconnect ana@example.com").
- An item's label is its text, and spans laid out side by side don't add spaces. Put `{" "}` between them, which the flex layout ignores, so "Show all results" and the query don't read as one word.

## Tests

The renderer has no automated tests. Kisa's suite covers the mail engine, the store, credentials and message privacy; check interface changes by hand in the running app, including keyboard paths and the names agents see in `createAgent().snapshot()`.
