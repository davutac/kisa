# Desktop architecture

Kisa follows the Electron boundary used by t3code: shared runtime contracts, a narrow preload bridge, schema-validated main-process methods, a central handler installer, and renderer adapters that hide the host transport.

The comparison and source links are recorded in [`../research/t3code-electron-architecture.md`](../research/t3code-electron-architecture.md).

## Main-to-renderer communication

```text
React feature / hook
  -> renderer platform/desktop.ts
  -> window.desktopBridge
  -> preload capability module
  -> ipcRenderer.invoke
  -> main/ipc/desktop-ipc.ts
       decode request with Effect Schema
       run capability method
       encode result with Effect Schema
  -> renderer
```

Events take the reverse path. `main/electron/renderer-events.ts` encodes the payload before sending it; `preload/subscribe.ts` decodes it before notifying a renderer listener. Every subscription returns an exact unsubscribe function.

Conversation popouts use the same boundary. The main mailbox requests an account-scoped thread window through a schema-validated IPC method, and only closes its inline conversation after the new window's renderer has loaded. Each popout loads the dedicated `/thread/$accountId/$threadId` hash route, reuses the existing mail bridge, and has minimal window chrome. A second request for the same account and thread focuses the existing popout; the main window remains the explicit target for app activation and notification-click fallback.

The app-wide Animations, "Run in background", "Always open threads in new windows", and "Keep images from opened emails" preferences live in one `app-settings.json` file under the user data directory. A file written before "Keep images from opened emails" existed keeps its values and keeps images for 90 days. Main loads them once before creating the window, and the renderer receives the hydrated settings in its app-start reply. Opening Settings therefore does not trigger another read or render temporary default values. Updates change in-memory behavior immediately, while asynchronous file writes are debounced and flushed during orderly shutdown. Theme remains renderer-owned: a ui-sdk color scheme (`createColorScheme`) kept in `localStorage` under `vite-ui-theme`, the key and values next-themes used before it, so a saved choice carries over. It starts dark, sets the `dark` class on `<html>` that `main.css` styles by, and follows the system while System is chosen. The main, Add account, and attachment preview windows share it, and a choice made in one reaches the others through the storage event.

Animations default to enabled. A shared provider applies the preference to the main, thread, and attachment-preview renderers. Disabling it removes CSS animations and transitions and configures Motion for reduced motion; enabling it restores motion while preserving the operating system's reduced-motion preference. "Always open threads in new windows" changes the default for mailbox clicks, the mailbox open command, and search results, while the explicit inline popout action remains available when the preference is off.

"Run in background" defaults to enabled. When enabled, closing the main window hides it to a system tray icon instead of quitting, so mail synchronization and notifications keep running. On macOS, the Dock icon is also hidden while no Kisa windows are visible and restored with the window. When disabled, closing the last open window quits the app on every platform, including macOS. The tray menu restores the window or quits.

"Launch at login" is available on macOS and Windows, the platforms supported by Electron's login-item API. The operating system owns this value. Settings reads it on mount, writes changes through a narrow IPC method, and displays the value Electron reports after each write. Kisa does not copy it into `app-settings.json`, so changes made in macOS System Settings or Windows Startup Apps remain authoritative. A macOS login item that requires approval stays off and explains the required System Settings action.

## Ownership

```text
apps/desktop/src/
  main/
    app/        lifecycle and activation handling
    auth/       accounts, the Add account window, and sealed credentials
    electron/   Electron adapters used by capabilities
    ipc/        transport runtime, method definitions, central installer
    mail/       mail engine runtime, IMAP and SMTP adapters, message presentation
    updates/    updater state machine and Electron updater integration
    window/     native window state
  preload/      the only renderer exposure of privileged capabilities
  renderer/     React application, feature UI, state, and host adapters
  shared/ipc/   channels, Effect Schema codecs, and DesktopBridge contract
```

Feature services do not register `ipcMain` handlers. Each public operation is a declarative method under `main/ipc/methods`, and `desktop-ipc-handlers.ts` is the single reviewable list of privileged calls.

Packaged self-updates are user-driven after discovery. The main process checks in the background and publishes an available version without downloading it. The title bar and Settings expose the same sequence: download on the first action, show bounded progress, then request renderer-wide confirmation before the install action closes and restarts Kisa. Automatic download and install-on-quit remain disabled, and the main lifecycle accepts download and install calls only from their matching states.

The renderer does not import main or preload modules and does not call Electron directly. Components use feature hooks or `platform/desktop.ts`; browser mode is represented by an absent optional bridge.

The local SQLite database uses the `better-sqlite3-multiple-ciphers` implementation with a fixed ChaCha20 configuration. Main generates a 256-bit key, seals it with Electron `safeStorage`, and stores only the sealed blob beside the database. Development uses `mail.dev.sqlite` and `mail.dev.sqlite.key`; packaged builds use `mail.sqlite` and `mail.sqlite.key`. The mail engine started this file afresh; the earlier `app.sqlite` and `app.dev.sqlite` files are never opened. On Linux, main configures Chromium's password store before Electron becomes ready: desktops with a known secure automatic selection keep it, while LXQt and unrecognized sessions request Secret Service through `gnome-libsecret`. Explicit command-line selection remains authoritative. After startup, Kisa accepts only libsecret or KWallet backends and rejects `basic_text`, `unknown`, and failed secure-store fallbacks.

Main sends the unlocked key to the database utility process as its first private process message; it never enters renderer IPC, process arguments, environment variables, or logs. The utility applies the key before any query or migration and erases its key buffer after opening the connection. Existing plaintext databases are checkpointed, switched out of WAL, and encrypted in place with `rekey` before normal startup continues.

Database RPC results are always arrays of rows. Queries that need at most one row remain bounded with `LIMIT 1` and select the first returned row in main; scalar proxy `get` execution is rejected so an empty result cannot be confused with a row whose fields are `undefined`.

Parameters and rows cross the database RPC by structured clone, which keeps bytes and big integers as they are, so they are not encoded: each side checks what arrives with one pass of guards (a string, finite number, boolean, null, big integer or bytes in every cell) and passes it on unchanged. A schema per value had cost several times the round trip itself on every statement. The database process keeps the 200 statements it prepared most recently, by their SQL, since Drizzle sends the same text for the same query shape. Its connection keeps a page cache of up to 128 MB, filled only as pages are read: a mail cache with bodies runs to hundreds of megabytes, and every page read again after leaving SQLite's 16 MB default cache had to be decrypted again, which was most of what a search spent its time on.

The Database settings section exports a versioned `.kisa-key` recovery file and imports an existing Kisa database with that key. A blocking overlay accepts each file through a native picker or drop target, then reports coarse progress after the user starts the import. Selected paths remain behind an opaque main-process session; the renderer receives only display names, and preload resolves dropped `File` objects without exposing their paths. Import copies and validates a private staged database in an isolated utility process. A clean restart activates the staged files and, once the import is active, preserves the previous database, sealed key, and journal sidecars under `database/backups/`; interrupted activation resumes on the next startup. Whether an import is waiting for that restart is one fact, the staged import's manifest file: main reads it whenever it is asked and keeps no copy, and the renderer shows only what main answers, which carries no path. While one waits, the Database section shows a row saying Kisa is still using the current database, with Restart now (Quit now in development) and Discard import. Discard removes the manifest before the staged copy, so an interrupted discard cannot leave a manifest pointing at missing files, and it is refused while an import is running. The manifest records how far activation has got: `pending` while nothing is swapped, `swapping` once the backup is complete and the swap has begun, and `restoring` while a failed swap is being undone. Each step is written by renaming a new manifest over the old one, never by removing it first. A start decides from that record. An import that fails before the swap, because its manifest does not decode, its staged files are gone or its backup cannot be made, is dropped: Kisa starts with the current database, which was not changed, and removes that import's own unfinished backup. A swap cut short by a crash is carried on, without making the backup again, since the active file may by then be the imported database. A swap that fails is undone: the backup's database, key and journal files are moved back, not copied, because a full disk is the likely cause, and Kisa starts with the previous database; that empties the import's backup folder, which is then removed. If a begun swap can neither finish nor be undone, because the backup is not whole, the start fails and nothing is deleted. A dropped or undone import is announced once at that start, in a dialog attached to the main window, shown when the window is if it starts hidden. A manifest written before steps were recorded keeps its earlier rules and is never dropped or undone on that account. Each backup file is copied under a temporary name and takes its real name only when whole, and a backup file that exists is never written again. Staged copies that no manifest names, left by a crash or a quit during an import, are removed at the next start; the match is exact to this database's own staged names. Quit stops an import that is still copying or validating, and ignores an answer to its restart prompt that comes after quit began. Packaged builds can relaunch automatically. Development quits instead because `electron-vite` owns the renderer server, and the user reruns the development command.

The Database section also chooses how long images kept from opened emails last once they stop being shown: 30 days, 90 days (the default), a year, or forever. See [Mail engine](mail-engine.md) for how they are kept and cleared.

## Renderer organization and routing

The renderer follows the same broad shape as t3code's web app: feature-oriented component folders, domain logic outside React components, a `state` folder for application-wide context, and a small `platform` adapter around the host bridge.

```text
renderer/src/
  components/
    accounts/   authentication and account controls
    mail/       mailbox and conversation presentation
    shell/      sidebar, title bar, theme, and app chrome
    startup/    startup boundary and splash UI
    updates/    update presentation
    ui/         generated design-system primitives
  mail/         mailbox model, queries, and feature hooks
  platform/     environment-neutral access to desktop capabilities
  routes/       TanStack Router file routes
  startup/      startup session model
  state/        renderer-wide providers
  updates/      update state presentation model
```

`main.tsx` selects TanStack Router history before rendering: hash history inside Electron and browser history for the web fallback. `router.ts` owns router construction and type registration, and `App` mounts `RouterProvider` immediately.

As in t3code, route lifecycle code is reserved for navigation gates and initial bootstrap state. The root route's `beforeLoad` starts the desktop runtime and resolves the initial authentication state; its pending and error components own the startup splash. Live product data remains in renderer state modules and feature hooks: the mailbox list uses `useMailboxThreads`, and the thread route uses `useMailThread`. A mailbox whose first page cannot be read says so and offers Try again in place of its empty state; with conversations already listed, the failure and Try again follow the last row, and reaching the end of the list asks for no more until it is retried. Try again after a row is not reached by `Tab`, which moves between conversations; on an Inbox, its `Mod+1`–`Mod+9` shortcut reloads it, and other places have no keyboard retry. Reading the first page again replaces the rows within its range, so a conversation that left the place while the list was not watching does not stay listed; when a list event arrives during that read, the page is merged instead and read once more, so new mail is not dropped. A search that fails says so, with Try again, rather than showing no matches. This keeps routes declarative while allowing IPC events to update mounted screens without invalidating router loaders.

React Compiler compiles the production renderer, and Ultracite's React rules report code it cannot compile. Components and hooks do not write `try`/`finally`: async handlers pass their cleanup to `runWithCleanup` in `lib/run-with-cleanup.ts` and keep any `try`/`catch` inside the task. A value that must be created once per mounted instance and never replaced, such as a keyed composer's store or a dialog's opening time, uses `useInstanceValue` instead of `useMemo` with an empty dependency list, because React may discard memoized values. An effect dependency that exists only to re-run the effect carries a line-level suppression that names the trigger.

The main window is a sidebar beside a content column. Dragging the sidebar's trailing edge resizes it, up to 360 pixels so the content column stays usable at the window's minimum width, and down to wherever its titlebar strip still shows the app name in full; that minimum is measured from the strip, so it follows each platform's window-controls inset. The edge is also a focusable separator: the arrow keys step it by 16 pixels, Home and End jump to either limit, double-clicking it restores the default 240 pixels, and Escape during a drag puts the width back. Resizing follows the pointer without easing, while showing and hiding the sidebar still animate. The sidebar's titlebar strip holds the sidebar toggle, the app name, and Go back and Go forward. Those two step through the sidebar places visited in the window: a mailbox or label in an account scope, Scheduled in a scope, Templates, or a new email, which opens blank when stepped back to. Settings is not a place: it is a dialog over whichever place is on screen. Opening a conversation is not a step, because Escape already closes it. A step changes the scope only when its place needs another one, so going back from Templates keeps the open conversation and the Unread filter. Steps skip places whose account has been disconnected, a label its scope no longer has, and Scheduled once nothing is scheduled. The history lives only in memory and keeps the last 50 places, and a step whose route never arrives still ends, so recording resumes. Below that strip, the sidebar opens with one row: mail search, styled like a sidebar row with its shortcut in the tooltip, followed by the Unread filter and New email as quiet icon buttons. New email opens a new email as its own page, the way Templates opens its own: it reads as pressed while that page is on screen, and pressing it again leaves the page the way Escape does. Search opens a command bar over the window, and `Mod+K` opens it from anywhere, even with the sidebar hidden. The bar edits its own copy of the query, with filter pills and completions. As in Gmail's search box, its first item is Show all results, so Enter after typing always hands the query to the mailbox list, however far the matches have loaded. Below that item it lists up to eight matching conversations; arrowing to one and pressing Enter opens it, in a new window when that preference is on. Searches carry the mailbox view's scope (Sent, Spam, Trash or a label, and the Unread filter), which the bar names in its footer and empty state. A label scopes the search by its id rather than its name, so a folder called "Spam" is searched as that folder and not as the Spam mailbox. While the list shows results, the Search row names their query and reopens the bar to refine it, a × beside it clears them, and the bar offers Clear search results. Leaving the mailbox or hiding the sidebar also ends them. With the sidebar hidden, its toggle, Go back and Go forward, and New email as a filled button move to the content titlebar. Below that row come the favorite labels, Scheduled while scheduled mail exists, the account scopes, and a footer holding the Settings button, which opens the Settings dialog, and the Templates workspace button, with Add account at its trailing end. Just before Add account sits a round update button wherever the app can update itself: a refresh icon that checks for updates, spinning while it checks, and once an update exists, a filled download icon, a progress ring while it downloads, and a restart icon to install it. Its tooltip names the state and version. It hides with the sidebar; Settings offers the same actions. The account scopes carry no heading of their own. All accounts is a single row for the combined Inbox with nothing to disclose, and reads as current whenever the all-accounts scope is on screen; its Sent, Spam, and Trash stay reachable through their shortcuts. Each account (reorderable by dragging its icon, which turns into a grip on hover; the icon is a button of its own beside the row, so Tab reaches it and Space or Enter picks the account up, the arrow keys, Home and End move it, Space or Enter drops it, and Escape puts it back, while a plain click on it, like on the rest of the row, opens the account; the numbers follow the order once it is dropped, and a move in progress ends if an account connects or disconnects) stands for its Inbox and discloses its own Sent, Spam, and Trash rows and a Labels row: choosing an account away from its Inbox opens that Inbox and shows its mailboxes, while choosing it with its Inbox on screen only shows or hides them; with a conversation open over that Inbox, choosing the account, All accounts for the combined Inbox, or its shortcut closes the conversation as Escape does, keeping the list's filter, selection, and scroll and leaving the mailboxes as they are; and the `Mod+1`–`Mod+9` shortcuts, numbered down the sidebar from All accounts, open the Inbox without changing what is shown; holding `Mod` reveals each row's `Mod` shortcut; every account starts closed. The Labels row, shown only when the account has user labels, discloses them nested by their `/`-separated paths; a label whose parent path is not a label itself hangs from the nearest one that is and keeps the rest of its path. It starts closed, so a long label list never pushes the accounts below it down. A label is a place like Sent: it lists every conversation carrying it outside Spam and Trash, whether or not it is in the Inbox, as Gmail's label view does, and choosing it again returns to the account's Inbox. Labels match without regard to case. A label with an unread conversation on its place carries the red unread dot that Spam carries for unread spam, and so does its favorite; the label rows ask the cache for it only while they are shown, one read at a time, and a burst of thread updates, such as the background index sends, costs one more read half a second after the last. While the labels are hidden, the Labels row shows the dot for any of them, so unread mail behind it stays in sight; once they are shown, it gives the dot back to them. A parent label's dot reflects only its own conversations, since its place does not list its children's. A label place whose label its scope no longer has, after a rename, a delete, or a scope switch, moves to that scope's Inbox, but only once every label catalog in the scope has loaded: a catalog still loading or one that failed keeps the place. Hovering a label row, or tabbing to it, shows a star at its trailing edge, a button beside the row rather than inside it, filled for a favorite; it adds the label to the favorites or takes it out. Favorites list in the order they were added, each opening its account's label place and naming its account in its tooltip, and in the row itself when two accounts' favorites share a name; a favorite's own star takes it out. A favorite of a disconnected account, or one whose label its account no longer has, is not shown. While a favorite shows the place on screen, it alone reads as current, and the account tree leaves its rows plain. An account row's icon is its provider's logo, from [svgl](https://svgl.app): Gmail's, Outlook's, or Apple's for iCloud, chosen in main from the stored provider and, for a custom domain stored as plain IMAP, from its IMAP server, so a Google Workspace or iCloud+ domain still shows its provider; any other server keeps a person icon. The composer's From picker, each account's Settings page, and conversation rows in a view that mixes accounts show the same logo. The icon gives way to a spinner while the account syncs, to a progress ring while it indexes, and to an alert while its sign-in is refused, so every row icon keeps one size and column; a refused account's tooltip points to Settings, where Sync now tries the sign-in again. While the sign-in is refused, the account's Mail sync row in Settings offers Sign in again, which opens the Add account window for that account: an app password account types only a new password, which main checks against the account's stored servers and user name, and a Microsoft account signs in in the browser. Either keeps the account's mail. Main decides which account and which way when it opens the window, and refuses a submission for any other. An account row reads as current while its Inbox shows its scope, and while its Sent, Spam, Trash, or a label is on screen with those rows hidden; once they are shown, the current mailbox row reads as current instead, and for a label the Labels row does until the labels are shown too. The content column's titlebar holds indexing progress, so collapsing the sidebar never hides it. A view may put its own toolbar in the middle of that titlebar through `TitlebarSlot`, a portal the shell provides, instead of adding a row under it: the mailbox puts its breadcrumb there: the account scope, then the mailbox, or a label split where the labels above it are labels themselves, as the sidebar nests them. The scope opens its Inbox and a parent label opens that label, so the path can be climbed with the sidebar hidden. A conversation open over the mailbox extends the breadcrumb with its subject, turns the mailbox crumb into the way back to the list (as Escape is), and puts its date and actions (Mark as read or unread, Trash or Delete forever, Not spam in Spam, and Open in new window) on the titlebar's trailing side, so the conversation itself starts with its labels row, which sticks to the top as the messages scroll. The breadcrumb and the actions are one `MailboxBreadcrumb` in the slot, not two portals, and the conversation registers its shortcuts itself, so they hold wherever its buttons are shown. A pop-out window has no titlebar to fill and keeps the subject and actions in a sticky header card. A page that has a title uses `PageTitlebar` instead, which sets the title on the leading side and the page's actions on the trailing side in the same slot: Scheduled names itself and the account its scope filters to, Templates its New template and Save actions (Save submits the editor form by id, since the titlebar sits outside it), and the new-email composer its Stash, stash picker, Send, and Schedule actions. The space around a view's controls stays a window drag area, while the controls and the breadcrumb's links opt out of it. Both titlebars share the window's drag strip: the sidebar header clears the macOS traffic lights and the content titlebar clears the Windows and Linux overlay controls, taking both insets while the sidebar is hidden. Every window's titlebar, including the pop-out thread, attachment preview, and Add account windows, is a `WindowTitlebar`, which keeps its content between whichever window controls it sits beside; the insets themselves come from the window-controls overlay through `.app-titlebar` in `main.css`. `AppShell` owns navigation and every navigation shortcut the sidebar advertises, so a hidden sidebar stays mounted but inert and zero-width rather than unregistering them. A new email is the `/compose` route, a page like Scheduled and Templates, so while it is on screen New email alone reads as current and no account, mailbox, or workspace row does. It starts from the account scope it was opened from, puts its title and actions in the titlebar slot like any page, and closing it after Send, Discard, or Escape returns to the view it was opened over, as closing Templates does; that view remounts, so it keeps its scope, open conversation, and Unread filter but not its scroll position. Opening another workspace from a new email remembers the view the email was written over, so closing that workspace never lands on a blank email. Every way off the page, whether a sidebar row, a shortcut, Go back, or another page, passes a router blocker that first keeps anything written in the stash; while the composer is busy, or if the save fails, the navigation is cancelled and the page and its draft stay on screen. A scheduled email opens in the same composer page, laid over the Scheduled list as a conversation is laid over the mailbox, so the list keeps its scroll and selection underneath and Escape returns to it. Its title is a breadcrumb like a conversation's, Scheduled then the subject, where Scheduled returns to the list as Escape does, and its actions are Discard, Save, the persisted send time, and Send now or Reschedule; its blocker never stashes, since the email stays queued, and instead asks before abandoning unsaved edits or a chosen new time. Whether the sidebar is open, its width, which accounts show their mailboxes and labels, and the favorite labels are layout conveniences kept in the renderer's `localStorage`: unreadable or malformed values fall back to an open 240-pixel sidebar with every account closed and no favorites, a stored width outside the limits is clamped to them, and these lists are rewritten whenever accounts change so a disconnected account's address and favorites leave storage with it. The Unread filter is kept there too, so it stays on through every account and mailbox switch and across restarts until its toggle or `U` turns it off; choosing the Inbox already on screen reloads it without clearing the filter, and an unreadable value leaves the filter off. Pop-out thread windows have no sidebar.

Settings is a modal dialog over the main window, not a route, so the place underneath, with its scope, open conversation, scroll position, and Unread filter, is untouched when it closes. `AppShell` owns it through one dialog controller: the sidebar footer's Settings button is a trigger connected to that controller, and `Mod+,` opens it, so both work while the sidebar is hidden. Escape and its Close button close it and return focus to where it was; while it is open, ui-sdk pauses every application command, `Mod+,` included. It is centered with the same margin above and below, the titlebar strip's height plus 0.75rem, so it never covers the strip or the Windows and Linux window controls. A column of pages, a vertical `Tabs` list, sits beside the selected page, which is named after Settings in the dialog's header: General (Appearance with Theme and Animations; System with Launch at login, Run in background, and Updates; Conversations with Always open threads in new windows; then the versions), AI writing (Provider and Instructions), Data (Database and Images), and, under an Accounts heading, one page per account in sidebar order (Mail with New email notifications, Email signature, and Automatic categorization; Labels; Sync; Disconnect), followed by an Add account button. Above the pages sits a search, which `/` focuses. It finds pages and settings in a static index (`settings-search.ts`) of each setting's title, its page's name and a few keywords, so typing "dark" finds Theme, an address or display name finds that account's settings, and "signature" finds every account's. Every word typed must match; a title that is the query, then one that starts with it, then one that holds every word rank first, and ties keep the dialog's order. While it holds text, its results replace the pages, each naming its page. Choosing one shows that page, clears the search, scrolls the setting's row to the middle and focuses it, highlighted until focus leaves it; a row on a page that loads first, like AI writing, is reached once it appears. The index lists only what the runtime shows, as the pages do. A page appears only where the runtime offers its capability, so the web fallback shows General alone. Only the selected page is mounted, each page scrolls itself, and the dialog reopens on the page it was left on; that choice lives only in memory, and a page that disappears, such as a disconnected account's, gives way to General. Dialogs opened from a page, such as Email signature, Reply instructions, the database import overlay, and confirmations, stack above it, and answering one leaves Settings open.

Destructive and interrupting actions use the renderer-wide `ConfirmDialogProvider`. Features call `useConfirm()` with their copy and await a boolean result instead of owning dialog-open state. The provider serializes overlapping requests, restores focus after the queue drains, resolves pending requests as cancelled when it unmounts, and can require exact confirmation text for especially destructive actions. The shared view owns the confirmation layout and keyboard behavior: Escape cancels, while Enter confirms once any required text matches. The operation itself starts only after the dialog resolves.

Mail dates follow desktop mail convention. Lists show today's time, then "Yesterday", a weekday for the past six days, a month and day for the current year, and a full date for older years; message, reply, scheduled-delivery, and label-sync dates add the time to every day, while the conversation's date, in the titlebar or a pop-out window's header, keeps the compact form so the subject keeps its room. Buckets are calendar days in the current time zone, so a message from 23:50 reads "Yesterday" just after midnight, and a bare weekday is never used for a future date. Hoverable dates spell out the full date and time in a tooltip. Dates in mailbox rows and message headers sit under the row's activation button, where a tooltip could never open, so they render as bare `<time>` elements and the full date reaches assistive technology through the row's accessible name or the element's label. Wording, including "Yesterday" and 12- or 24-hour time, comes from the renderer's Intl locale like Kisa's other dates; Electron derives that from the system language rather than the macOS region or clock setting, so a German system shows "Gestern" beside English interface text.

One shared calendar holds the current day and system time zone. A midnight timer would run late after sleep, when Chromium pauses timers, and would miss a time-zone change, so the calendar is re-read every minute while dates are on screen and whenever the window regains focus. Visible dates re-render only when the day or zone actually changed. Formatters are built for that zone, so travelling cannot leave wall-clock times or day buckets from the startup zone, and a system zone that Intl cannot load by name falls back to the implicit default zone.

Mailbox rows separate read from unread mail without fading the row, which would drop muted text below readable contrast. Unread rows set sender and subject semibold at full foreground color and add a small dot before the date; read rows use regular weight and slightly muted text. Labels and attachments keep full contrast either way, and the row's accessible name includes the unread state and conversation size. Scheduled rows use the read-row treatment.

Rows listed in a mailbox omit that mailbox's own system label, rows listed under a label omit that label, and the Sent mailbox omits the sent marker, because every row would repeat them; search results keep them because they span mailboxes. A row names its account only when the view mixes several connected accounts, and so do the search bar's conversations: its provider's logo beside its full address, which the row's label also announces.

Footer and dialog actions follow one hierarchy: the action a surface exists for (Send, Schedule, Save template, a dialog's confirm) is the filled primary button; alternatives and cancels are secondary or outline; and a labelled action that deletes data, such as Disconnect, uses the destructive variant before its confirmation, while icon-only delete actions (Trash, bulk Trash, Discard draft, Discard scheduled email, Delete template) stay neutral at rest and turn red on hover so they never outrank the action beside them. Footers share one order: icon tiles (Stash, Discard, Delete) lead, the primary fills toward the trailing edge, and only the primary's own option, the Schedule trigger, follows it. Composer and template footers start disabled more often than not (no recipients yet, nothing to save), so their primary rests at the secondary level until it can run, keeping an inert control from being the loudest thing on screen. Conversation actions (Reply, Reply all, Forward) stay equal peers.

## Optimistic thread actions

Every thread action shows at once and the server catches up: mark read or unread, Trash, Delete forever, Not spam, adding or removing a label, each alone or on a selection, and their Undo. `useThreadActions` puts the change in the window's pending-change store (`mail/pending-thread-changes.ts`) before it asks main, and takes it out when main answers. The mailbox list, search results, and an open conversation lay the pending changes over the rows they hold as they render: a trashed conversation leaves the Inbox and joins a loaded Trash, a conversation deleted forever disappears, and read state and labels change in place. Only what is shown runs ahead. Paging cursors, snapshots, and the next read keep the cache's rows, so once the action answers, the view shows the cache again. Main publishes a change's thread list event before it answers the action, with the acted-on conversations first in it, so a confirmed change does not flash back, and a refused one returns to what the cache still has, with the error. Search results apply thread list events to the rows they show for the same reason, and leave or gain rows only when the search runs again.

Opening an unread conversation shows it read at once as well, while main marks it read. The conversation itself shows as soon as the cache can answer, with the inline images kept from an earlier opening; images seen for the first time follow from the server (see [Mail engine](mail-engine.md)). The inline conversation closes as soon as it is trashed, deleted, or marked not spam, and mailbox focus moves to the row that takes its place. A pop-out window is the exception: it closes only once the server agrees, since a closed window could not report a failure.

The store belongs to one window; other windows see a change when main confirms it. Feedback comes with the change: its toast appears at once and becomes the error if the server refuses it (see [Undoable actions](undo.md)). Indicators that the cache answers with queries of their own, namely the unread dots on labels and accounts, Spam's dot, and the Dock badge, follow the confirmed change rather than the pending one. Two kinds of server work deliberately wait for the answer. Sending keeps the composer open until the server accepts the message, because a refused or unknown outcome must leave the message where the user can act on it. Creating, renaming, and deleting labels wait too: the server assigns a label's id, can refuse a name, and, for a folder, first moves its mail.

## Security boundary

The renderer is sandboxed with context isolation. Preload exposes only the application-owned `desktopBridge`; the generic Electron toolkit API is not available to page code. Unknown renderer inputs are decoded in main, and main-to-renderer event values are decoded again in preload.

An account signs in with an app password, or, for Outlook.com and Microsoft 365, with Microsoft in the system browser. An app password is typed into a separate Add account window with its own preload and crosses IPC once, write-only, to main, which verifies it against the account's IMAP and SMTP servers and seals it with `safeStorage`. A Microsoft sign-in sends that window's address only: main opens Microsoft's page in the browser, receives the redirect on a temporary loopback listener, and seals the refresh token it gets. The mail window's bridge can list, reorder and disconnect accounts, open the Add account window, and open it to sign a connected account in again, but never carries a credential. Sign-in goes straight to the provider; Kisa runs no server of its own. The [mail engine](mail-engine.md#accounts) documents that boundary.

Message HTML is displayed in a `srcdoc` iframe sandboxed without scripts, under its own `default-src 'none'` policy; `renderer/src/mail/email-frame.ts` builds that document. Displaying a message must not tell its sender that it was opened until the reader allows it:

- Remote images stay blocked until the reader shows them for that message or always shows them for that sender. A From address is the sender's own claim, so the standing choice applies only when Gmail authenticated the sender's domain, and never in Spam; otherwise the notice offers only the one-time choice.
- Shown images load over HTTPS only. `http:` URLs are upgraded first, so a plain-HTTP device on the reader's network receives no request. Requests from message frames send no cookies and store none, so a cookie cannot tie one opened message to the next, and main removes their `Referer` header, because an element's own `referrerpolicy` overrides the frame's `no-referrer`; the image host still sees the reader's IP address.
- Every `<link>`, `<meta>` and `<iframe>` start tag becomes an inert `<param>`, which Chromium does not render, because each acts while the message is parsed, outside the reach of the frame's policy. The tag is renamed, not removed, since removing text can join what is left into a new tag. Chromium resolves `rel="dns-prefetch"` hosts despite the policy. An `<iframe srcdoc>` is a second document that `frame-src` does not stop, and a `<link>` entity-encoded inside it is resolved the same way. A message's `<meta name="referrer">` would replace the frame's own.
- A BIMI sender logo that is not already cached is looked up only when the message would show that sender's images automatically, because the lookup queries the sender's DNS and fetches from a host their record names. The logo always comes from the domain's own record, never from a `BIMI-Indicator` or `BIMI-Location` header in the message. Notifications use cached logos only.

Whether Gmail authenticated a sender is read from the topmost `Authentication-Results` header only, and only when it names `mx.google.com`: Gmail adds its header above every header a message arrives with, so anything lower was written by the sender. The result is recorded when a message is parsed and cached with it, so a thread opened from the cache applies the same rule; messages cached before the result was recorded count as unauthenticated until they are fetched again.

A message's web links and image-map areas open in a new window, which main hands to the system browser only for `http:` and `https:` URLs; other links, including SVG links, are disarmed, and `ping` and `download` are removed. The frame is prepared this way as soon as the message is parsed, not when it has loaded: the `load` event waits for every image, and an image host that answers slowly or never would otherwise leave the links as the sender wrote them and the frame at its minimum height. The frame's `<base target="_blank">` gives links the same destination before that. The page's `frame-src 'none'` and main's `will-frame-navigate` handler each stop the frame from navigating anywhere but its own document, so a link cannot load `file:` URLs or reach a network share; a link that tries is refused and replaces the message with an error page, which is why none is left to try.

These rules rest on how Chromium treats hostile markup, which reading the code cannot settle. They were checked by loading such messages through `email-frame.ts` in a real sandboxed frame, under the page's own policy and from both a `file:` and an `http:` page, while recording the network log: with images blocked a message causes no lookup or request, with images shown only HTTPS image requests without cookies or a referrer, and in neither case does any script run. A change to the frame, its policy or the patterns above needs the same check, not only a unit test.

Expressions that scan message HTML or headers in main or the renderer must stay linear in their input: a pattern whose neighbouring parts can claim the same characters lets a few kilobytes of crafted markup stall the window or the main process.

The sandbox preload is emitted as CommonJS and bundles its non-Electron dependencies. Sandboxed Electron preloads cannot load the application's ESM entrypoint or resolve arbitrary package imports at runtime. If Electron starts without the bridge, the root route now reports a startup failure instead of silently rendering the browser fallback with an empty account list.

On quit, the main process sends a typed closing event before stopping mail synchronization and waiting for the database and IPC runtimes to dispose. Every quit request is held until that cleanup has ended, so asking to quit a second time cannot cut the database close short. A cleanup step that fails does not stop the steps after it. Cleanup runs in ordered stages of at most 10 seconds each: a stage still running then is left behind, so a hung stop can neither skip the database close nor keep the app open. The database utility process exits once its server has stopped and SQLite has closed. Electron keeps a utility process alive while its parent port is open, so before it exited itself every quit waited out main's five-second close timeout and then killed it. A database that cannot be opened, under the wrong key for instance, ends the process the same way, so startup fails instead of waiting for an answer that never comes. The renderer keeps a route-independent closing overlay mounted so cleanup remains visible even when quit is requested during startup or from a non-mail route.

## Scope relative to t3code

t3code also has an HTTP/WebSocket RPC plane because its web client connects to local, SSH, WSL, and remote environments. Kisa has one desktop host, so adding a local server would duplicate Electron IPC without adding an environment boundary. If Kisa gains a standalone web client or remote mailbox backend, that is the point to introduce a shared RPC contract.
