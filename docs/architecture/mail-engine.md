# Mail engine

Status: in progress on `feat/imap-mail-transport`. This design replaced the Gmail REST backend, which is recorded in [the Gmail API capabilities](../research/2026-08-10-gmail-api-capabilities.md) and [the full-account indexing design](../research/2026-08-07-gmail-api-full-account-indexing.md). It is written as a new app: no existing cache, credentials or settings are migrated, and the engine uses a new database file.

Measurements behind the choices below are in [the Gmail IMAP probe](../research/2026-11-21-gmail-imap-probe.md).

## Goals

- **One engine for every provider.** Gmail and iCloud first, then any IMAP host with an app password, then Outlook. All of them go through IMAP for reading and SMTP for sending.
- **Useful within a minute of connecting.** The whole mailbox is listable and searchable by sender and subject long before every body has downloaded.
- **Local-first.** Lists, threads and search read SQLite. The network fills the cache; it is never on the path of a scroll.
- **Bounded and resumable.** Every background step works in small batches, commits before it advances, and can stop at any point.

## Non-goals for now

POP, Exchange EWS, JMAP, an offline change queue, calendar and contacts.

## Providers

| Provider | Incoming | Outgoing | Sign-in | Dialect |
| --- | --- | --- | --- | --- |
| Gmail | `imap.gmail.com:993` TLS | `smtp.gmail.com:465` TLS | App password (needs 2-Step Verification) | Gmail |
| iCloud | `imap.mail.me.com:993` TLS | `smtp.mail.me.com:587` STARTTLS | App-specific password | Generic |
| Google Workspace | `imap.gmail.com:993` TLS, by picking Gmail for the address | `smtp.gmail.com:465` TLS | App password, where the organization allows them | Gmail |
| Other IMAP | Entered by hand | Entered by hand | App password or password | Gmail if the server offers `X-GM-EXT-1`, otherwise generic |
| Outlook.com | `outlook.office365.com:993` TLS | `smtp-mail.outlook.com:587` STARTTLS | Microsoft sign-in (OAuth, XOAUTH2) | Generic |
| Microsoft 365 | `outlook.office365.com:993` TLS | `smtp.office365.com:587` STARTTLS | Microsoft sign-in (OAuth, XOAUTH2) | Generic |

Every account connects in the Add account window (see [Accounts](#accounts)). Gmail, iCloud and other IMAP accounts sign in with an app password: Gmail and iCloud addresses take their servers from a preset, an address on a domain whose mail Google hosts takes Gmail's, and any other address enters them by hand. Outlook.com and Microsoft 365 sign in with Microsoft in the system browser, because Microsoft's servers take no passwords from mail apps (`LOGINDISABLED`; refused for Outlook.com since September 2024).

**Outlook's IMAP server offers little.** Probed on 2026-11-22 without signing in, it advertises `IMAP4rev1 AUTH=XOAUTH2 LOGINDISABLED SASL-IR UIDPLUS MOVE ID UNSELECT CHILDREN IDLE NAMESPACE LITERAL+`: no `CONDSTORE`, `QRESYNC` or `SPECIAL-USE`. Its SMTP server offers `AUTH LOGIN XOAUTH2`. The engine therefore cannot rely on mod-sequences or special-use attributes; see [Staying current](#staying-current) and [Labels](#labels).

**Verified against real servers (2026-11-22).** Gmail, on a test account: sending with an attachment and a Bcc, finding the sent message by its Message-ID, a reply joining the same conversation, star, read state, a label created, applied, renamed, removed and deleted, archive and unarchive, trash and restore. After every change a fresh sync found the server agreeing with the cache. iCloud, read-only, about 1,500 messages: the generic dialect synced every folder in 18 seconds with no message lacking a `Message-ID`, and a second pass found nothing changed. iCloud offers `CONDSTORE`, `QRESYNC`, `IDLE` and `UIDPLUS` but neither `MOVE` (imapflow moves by `COPY`, `\Deleted` and `UID EXPUNGE` instead) nor `SPECIAL-USE`: its Sent, Trash, Junk, Archive and Drafts folders are recognised by imapflow's table of well-known names. Name-based roles are trusted only from servers without `SPECIAL-USE`, so a Gmail label called "Archive" stays a label.

**Removing single messages.** Moves use `UID MOVE` where offered, otherwise `UID COPY` and then removing the originals; a refused copy leaves the source untouched. With `UIDPLUS` the originals are removed with `UID EXPUNGE`. Without it a plain `EXPUNGE` would also remove mail another program marked `\Deleted` and kept, so those messages are unmarked for that moment and marked again afterwards, even if the expunge fails; if Kisa cannot tell which they are, or the server does not take the mark off them, it expunges nothing. MailCraft does the same.

A **dialect** is the only provider-specific code in the engine. It decides how a server's messages map to Kisa's identities and labels:

- **Gmail** uses `X-GM-MSGID`, `X-GM-THRID` and `X-GM-LABELS`. It syncs only All Mail, Spam and Trash, because every other Gmail folder is a label view of All Mail. An account that lists no All Mail cannot be read at all: see [All Mail hidden from mail apps](#all-mail-hidden-from-mail-apps).
- **Generic** syncs every selectable folder but the ones a server marks `\All` or `\Flagged`, derives identities from message headers, and threads locally. RFC 6154 expects those two to be views of mail that lives in other folders. Read as folders, what they show would count as a second copy of each message, and removing a label deletes the folder's copy when another copy remains, which here would be the only real one. The marks come from the server alone (imapflow guesses neither from a name), so a folder a user called "Flagged" is still a folder. A server that keeps mail only in such a mailbox, as Gmail does in All Mail, shows none of it under this dialect; none is known.

The dialect follows the server, not the address. An account gets the Gmail dialect when its IMAP server advertises the `X-GM-EXT-1` capability at sign-in, so a Google Workspace address, whose servers are Gmail's, gets it too; every other server gets the generic dialect.

## Identity

Every key below is scoped by account. An account is identified by its normalized email address.

### Messages

A **message** is one logical email. A **location** is one physical copy: `(mailbox path, UIDVALIDITY, UID)`. A message has one or more locations.

| Dialect | Message id |
| --- | --- |
| Gmail | `X-GM-MSGID` as a decimal string. Stable across moves between All Mail, Spam and Trash. |
| Generic | `h:` followed by a hash of the `Message-ID` header. When the header is missing, the hash covers the `Date` header, sender, subject and size, so the same copy always hashes the same way. |

How the three hard cases resolve:

- **A Gmail message moves from All Mail to Trash.** Its `X-GM-MSGID` is unchanged, so the message keeps its id and bodies. Its All Mail location vanishes and a Trash location appears.
- **Another client moves an iCloud message.** The copy vanishes from one folder and appears in another with the same `Message-ID`. A message left without a location is deleted only at the end of a pass, after every mailbox has been read, so the message survives and its bodies are not downloaded again.
- **One `Message-ID` sits in two folders.** That is one message with two locations, and it carries both folders' labels, except that a copy in Trash or Spam can take no part (see [Labels](#labels)). A change to the message (read state, trash) is applied to every location, which is Gmail's model too.

A message is deleted only when a complete pass over its account's mailboxes leaves it with no location.

### Threads

| Dialect | Thread id |
| --- | --- |
| Gmail | `X-GM-THRID` as a decimal string. |
| Generic | `h:` followed by a hash of the first `References` entry, else `In-Reply-To`, else the message's own `Message-ID`, else its message id. |

The generic rule needs no global state: by convention the first `References` entry is the root of the conversation, so a reply and its original reach the same thread id in whichever order they are fetched. A reply that carries only `In-Reply-To` to a message that is not the root starts its own thread. That case is rare and accepted.

### Labels

Messages carry label ids. Threads carry the union of their messages' labels, with one exception.

**Mail in the Inbox is always listed in the Inbox.** The list holds one row per conversation, and a row is in one of Trash, Spam and everywhere else, so when a conversation's messages are split between them, some take no part in its row:

- **A message in Trash, while another message is outside Trash.** Mail that arrives in a conversation after it was trashed belongs in the Inbox, as it does in Gmail; listed under Trash it would never be seen.
- **A message in Spam, while another message is in the Inbox.** The same mail, arriving in a conversation that was reported. Otherwise one message in Spam files the whole conversation there: the user's own replies stay in Sent when a conversation is reported, and those must not take it out of Spam.

The row (its labels, count, snippet and unread state) is built from the messages that take part, and opening the conversation shows those. The rule lives in `packages/mail/src/listing.ts`, and `tests/listing.test.ts` checks the guarantee for every way the messages of a conversation can be spread across Inbox, Sent, Spam and Trash. Three things follow:

- The message left out is not listed under Trash or Spam in Kisa until the rest of its conversation joins it.
- Actions still see every copy, so restoring a conversation brings such a message back, and trashing the rest and then undoing brings back the earlier one too.
- Rows written before this rule are found and rebuilt each time the engine starts, from the rows under Trash and Spam, which afterwards finds nothing.

**A message's copies are held to the same rule.** One message can have several copies: mail to oneself, the same mail delivered twice, a copy another program left in Trash. A message carries the labels of the copies it is listed by, and those are chosen as a conversation's messages are (`labelsOfCopies` in `listing.ts`): a copy in Trash takes no part while another copy is outside Trash, nor one in Spam while another is in the Inbox. So a message with a copy in the Inbox and one in Trash is Inbox mail, read or unread as its Inbox copy is, where it once carried both labels and was listed under Trash alone. A copy in Spam beside one in Sent still files the message under Spam, as reporting mail to oneself leaves it. A message with one copy carries that copy's labels, so nothing changes on Gmail, where a message is in exactly one of All Mail, Spam and Trash. `tests/listing.test.ts` checks this for every way one or two copies can be filed. Messages labelled before this rule are found each time the engine starts, from the copies in Trash and Spam whose message has a copy in another mailbox, and only those the rule labels otherwise are written, so a second start finds nothing.

**Where a row is listed is decided once, in main.** A row's labels and its four projections (`is_in_inbox`, `is_in_sent`, `is_in_spam`, `is_in_trash`) say where its mail is. Which places list it follows from them by one rule, `listingPlaces` in `apps/desktop/src/shared/mailbox-places.ts`:

- Spam and Trash list what they hold.
- Everywhere else lists a conversation only outside both: the Inbox and Sent by where its mail is, Starred and a label by what it carries, whether or not it is in the Inbox.

Main sends the rule's answer with every conversation, as `places`: one key for each place that lists it, such as `inbox`, `starred` or `label:work`. A window lists a row by asking whether its own place's key is among them, and asks the same of what a conversation's place allows (Archive, Star, Report spam, and whether Delete is for good). It never works a place out from the conversation's labels. Those are names for display, a user label by its path and a system one by its id, so a folder a server calls `TRASH` reads there exactly as the Trash mailbox does.

The cache's page query states the same rule in SQL, so a page is an index scan (`mailboxCondition` in `mail-reads.ts`). `tests/mail-thread-page.test.ts` holds the two together: for every place, over every setting of the four projections and a set of labels that includes capitals, letters outside ASCII and folders named like mailboxes, the pages list exactly the rows whose `places` holds that place's key. A label's case is folded as SQLite's `lower()` folds it, ASCII only, on both sides.

Two things stay outside this:

- **A change on its way to the server.** The window shows it at once, so for a row with a pending move it predicts the places with the same rule, from the labels the change will leave. Main's answer replaces the prediction when the server has answered.
- **Which labels the sidebar merges.** It joins labels across accounts by a case folding that also covers letters outside ASCII, which the page query and `places` do not. Two accounts whose labels differ only in such a letter's case share one sidebar entry that lists only one account's mail.

- **System labels** use fixed ids shared by every provider: `INBOX`, `SENT`, `DRAFT`, `SPAM`, `TRASH`, `STARRED`, `IMPORTANT` and `UNREAD`. The renderer already understands these.
- **User labels** use `u:` followed by the label's path, with `/` as the separator. For Gmail the path is the label name. For other providers it is a folder that has no special use.

How they are derived:

| Source | Gmail | Generic |
| --- | --- | --- |
| Inbox | `\Inbox` in `X-GM-LABELS` | A location in `INBOX` |
| Sent | `\Sent` | A location in the `\Sent` folder |
| Drafts | `\Draft`, or the `\Draft` flag | A location in `\Drafts`, or the `\Draft` flag |
| Spam | A location in the `\Junk` mailbox | A location in `\Junk` |
| Trash | A location in the `\Trash` mailbox | A location in `\Trash` |
| Starred | `\Starred`, or the `\Flagged` flag | The `\Flagged` flag |
| Important | `\Important` | Not available |
| Unread | No `\Seen` flag | A location without the `\Seen` flag |
| User label | Any other `X-GM-LABELS` entry | A location in a folder with no special use |

An Archive folder (`\Archive`) produces no label: archived mail is mail without `INBOX`, as it is in Gmail.

Every sync pass lists the account's mailboxes again, so a folder or label that another client adds, renames, or deletes reaches the catalog on the next pass, and its conversations follow as described under [Staying current](#staying-current). When the user labels differ from the cached ones, the catalog is announced as soon as discovery saves it, before the pass reads any mailbox, so a mailbox that fails later in the pass cannot swallow the announcement; every mounted view reloads it, as it does after a label change made in Kisa.

Gmail's category labels (Promotions, Social and so on) are not exposed over IMAP and are dropped. Label colours are not part of IMAP; Kisa keeps its own background colour per label. A user label gets one when the catalog refresh first stores it (and a stored label without one gets one on the next refresh): it looks random but is seeded by the case-insensitive name, so a label several accounts share has one colour in All Accounts. A colour chosen in Kisa is kept through refreshes and renames. The text colour is never stored: black or white, whichever contrasts more with the background, which always reaches 4.5:1.

## Schema

The engine writes a new database file. Tables are prefixed `mail_`.

- **`mail_accounts`:** address, provider (`gmail`, `icloud` or `imap`), dialect, display name (the sender name outgoing mail carries), sign-in name, the sealed app password, incoming and outgoing server settings, and sort order. Planned: a stored sync status with its last error. Today each account's loop keeps its phase in memory (syncing, indexing, idle, retrying, needs sign-in or stopped), and what the renderer is told is derived from it: the accounts in their catch-up pass as an event, and the index status, which reads `paused` once a sign-in is refused, `failed` once retries of an unreachable server have slowed to every five minutes, and `hidden` at once when the server lists none of the mailboxes the account's mail is read from. Each holds through the retries and clears only when a catch-up pass succeeds, so the views of indexing do not blink on each attempt.
- **`mail_mailboxes`:** account, path, delimiter, role, whether it can be selected, whether the dialect syncs it, `UIDVALIDITY` and `HIGHESTMODSEQ` (both stored as text), `UIDNEXT`, message count, the skeleton floor: every UID at or above it has cached metadata, and `null` means the walk has not started, and the flag cursor: on a server without `CONDSTORE`, where the next re-read of older flags begins.
- **`mail_message_locations`:** account, mailbox path, UID, `UIDVALIDITY`, message id, mod-sequence, flags, and the labels this copy gives its message. The primary key is `(account, mailbox, uid)`, with an index on `(account, message id)`.
- **`mail_messages`:** account, message id, thread id, `Message-ID`, `In-Reply-To`, first reference, received and sent dates, size, sender, `Reply-To`, recipients, subject, label ids, read, starred and draft state, attachment list, snippet, body state, plain text, gzipped HTML, remote-image flag, sender authentication, the version of the body format, and the few raw headers that sender branding, replies and unsubscribe need. The MIME structure itself is not stored. Columns are stored with the ones the engine reads most first and the bodies last: SQLite reaches a column by walking its row from the start, and a body, often tens of kilobytes in overflow pages, once sat between a message's id and its thread, sender and subject, so search, thread projections and lookups by message read every cached body on the way. The migration that moved them rebuilt the table, keeping rowids so the full-text index stays valid; the schema lists the columns in the same order because Drizzle recreates a table in its own. An index on sender address and name, with the date and thread, answers `from:` searches and sender suggestions without reading the table.
- **`mail_threads`:** the per-thread projection the list pages over: subject, snippet, latest date and message, message count, sender, unread state, labels, attachment list, when it first appeared in Spam, and indexed `is_in_inbox`, `is_in_sent`, `is_in_spam` and `is_in_trash` flags, each with a keyset index in the list's order. A partial index holds only unread conversations outside Spam and Trash, which the Dock badge, the sidebar's Inbox counts, and the labels' counts read; SQLite uses it only for queries that state those conditions as literals.
- **`mail_labels`:** account, label id, name, kind (system or user), backing mailbox path, and an optional local colour.
- **`mail_messages_fts`:** FTS5 over subject, sender address and body text, with `mail_messages` as external content, kept in step by triggers.
- **`mail_inline_images`:** account, message id, IMAP section, media type and bytes of an inline image a body shows, kept the first time its conversation is opened, and when it was last shown. The primary key is `(account, message, section)`, with an index on `(account, last shown)` so clearing unused images never reads them. Rows are deleted with their message and with their account, and an image is kept only while its message is.

A thread row is recomputed from its messages in the same transaction that changes them.

Every statement is a round trip to the database process, so a write is one transaction of a few statements however many messages it covers. A batch's rows, and the ids it looks up, are bound as one JSON parameter and expanded in SQLite with `json_each`: Drizzle builds a statement value by value, which for a skeleton batch had cost main more than SQLite took to run it, and one parameter keeps the statement's text the same for any batch, so the database process prepares it once. An update that gives each row its own values reads them from a materialized `json_each` table, which SQLite then joins row by row on the target's key; left as a plain join, it read every row's JSON once for each target in the mailbox. Body saves, whose HTML is bytes, bind theirs as a `VALUES` list instead.

SQLite plans these queries without statistics, so it must not be left a choice that reads every copy or message in an account to find a handful. Lookups by message start from the messages and reach their copies by message id through `CROSS JOIN`, which fixes the join order; the body queue picks its next messages from its own index before looking up their copies. `tests/mail-store-plans.test.ts` asserts those plans, since a wrong one still returns the right rows.

## Sync

### Connections

Each account has at most three IMAP connections: one for foreground work (opening a thread, a change the user made, attachments), one for background work (sync, skeleton, bodies), and one that only waits for a second mailbox's news (see [Staying current](#staying-current)). Calls on one connection run one at a time. Between cycles the background connection waits in `IDLE` (see [Staying current](#staying-current)); that wait is a call like any other, so the loop ends it before its next cycle. The connections are pooled per account in main, not held by the work supervisor. Disconnecting first suspends the account's work supervisor, which cancels the background loop and foreground work and waits for them, then closes every connection. Connections close together, and each gives its server at most a second to answer `LOGOUT` before its socket closes, so quitting or disconnecting never waits on a server that has stopped answering. Attachment downloads are the exception: they do not run under the supervisor, so closing the connection is what ends them. A connection unused for two minutes is closed. A refused sign-in, a lost connection, throttling or an interruption drops the connection, and the next use opens a new one. imapflow logging is off.

### Tiers

Background work runs in cycles on the background connection. A cycle first catches up with the server (see [Staying current](#staying-current)), then for up to 20 seconds alternates one skeleton batch with one batch of recent bodies. While work is left, the next cycle starts at once; when none is left, the loop waits for news from the server, or for the next poll where the server gives none. A body batch that stored nothing, because the server no longer has those messages, counts as no work left. So the tiers below overlap rather than run one after another.

1. **Discover.** `LIST` with special-use attributes at the start of every cycle, then a `STATUS` per synced mailbox. A server with `SPECIAL-USE` is trusted for roles. Without it, a role attribute the server sends anyway wins over one guessed from the folder's name, and a role an attribute claims is not given to a second folder by name; otherwise imapflow's name table decides, which knows Outlook's English and German names ("Sent Items" and "Gesendete Elemente", "Deleted Items" and "Gelöschte Elemente", "Junk Email" and "Junk-E-Mail", "Drafts" and "Entwürfe", "Archive" and "Archiv"). An action that needs a role no folder has (trash, archive, spam, delete forever, removing a folder label) fails before any server command; sending without a Sent folder files no copy. Gmail syncs All Mail, Spam and Trash; generic syncs every selectable folder that is not a view (`\All`, `\Flagged`). Mailboxes are read in priority order: Inbox and All Mail first, then Sent and Drafts, other folders, and Spam and Trash last.
2. **First screen.** Planned: the newest 50 Inbox conversations get metadata, structure and text bodies at once, so the list is useful within seconds. Today nothing is fetched specially for the Inbox: the skeleton walks Inbox and All Mail first, and bodies download newest first.
3. **Skeleton.** Metadata for every message, newest first, in batches of 500: identifiers, flags, labels, dates, size and the envelope. Generic also fetches the `References` header, for threading. UIDs are sparse, so each batch searches the 2,000 UIDs below the skeleton floor and widens the window fourfold until it holds a full batch or reaches UID 1. Each batch commits together with the new floor. One mailbox is walked at a time, in priority order. The whole mailbox becomes listable and searchable by sender and subject. The probe measured about a minute for 21,000 messages.
4. **Recent bodies.** Structure and text parts (never attachments) for mail received in the last 365 days, newest first, 25 messages per batch. A message with copies in several folders is fetched from one of those copies, by that folder's UID. Earlier builds could pair one folder's path with another's UID and store another message's body; a one-time migration therefore cleared every stored body on non-Gmail accounts, with the list's snippets and attachment summaries, and they download again.
5. **Everything else.** Opening a conversation downloads its missing bodies first, on the foreground connection; this also retries bodies that failed before. A body is marked failed when the server describes the message but returns none of its text, so the background queue moves past it; a failed body counts as done for the index's progress. A message some of whose parts came back keeps those and is done: a server that cannot serve one part would otherwise leave the message with no text at all. Once the skeleton is complete and no recent body is left to fetch, the background loop downloads older bodies, newest first, 25 at a time.

A snippet is the first 200 characters of a message's body text, with whitespace collapsed. A thread shows the snippet of its newest message that has one, and a thread with no body downloaded yet shows none. Planned: rows that scroll into view ask for their bodies at foreground priority.

### All Mail hidden from mail apps

Gmail lets a user leave a label out of what mail apps see: Settings, Labels, "Show in IMAP". Guides for other mail apps recommend unticking it for All Mail, which is the one mailbox the Gmail dialect reads an account's mail from. Each dialect says whether it can read an account from the mailboxes its server lists (`unreadable` in `dialects.ts`): Gmail's needs a selectable All Mail, and the generic dialect, which reads every folder, always can.

- **Adding an account** is refused when its mail cannot be read, with a message that names the setting. Connected like that, the account would sync Spam and Trash alone and report itself complete, with none of its mail.
- **A connected account** fails its pass before the mailbox list is saved, with `MailHiddenError`. A list without All Mail says the mail is hidden, not gone: saved, it would drop All Mail with every copy cached from it, and the bodies with them. So the cache stays as it is, and when All Mail is listed again the next pass carries on from where the account was, with nothing announced as new or downloaded again. Creating, renaming and deleting a label read the mailbox list after the server has made the change, so they fail with the same message once the server has taken it, and the label shows as it now is when All Mail is listed again.
- **What the user is told.** The account's index status reads `hidden` from the first failed pass, and Settings › Mail sync says that Gmail is not showing All Mail and which setting to turn on. It is never reported as an unreachable server, however long it lasts. The loop retries as after any failed cycle and on Sync now, so the account recovers by itself once the setting is changed.
- **Signing in again** is not refused for hidden mail. A new password is taken, and the account then says what to change, with one thing wrong instead of two.
- Tested against a fake server that keeps a mailbox and leaves it out of its list. That Gmail leaves a hidden All Mail out of `LIST`, rather than listing it as not selectable, is how the setting is documented and has not been tried against Gmail; either answer is read as hidden.

### Staying current

- **Waiting for news:** an account with no background work left waits in `IDLE` on its Inbox, on the background connection. imapflow's automatic `IDLE` stays off; Kisa starts each wait itself. Everything a server reports while it waits ends the wait, so what happens in the Inbox reaches the cache when it happens. On Gmail the wait is in `INBOX` although the dialect syncs All Mail: the Inbox is what the server reports on, and what follows a report reads All Mail.
  - **Mail arriving** starts a cycle, which caches and announces it and fetches its text.
  - **Mail leaving and flags changing** (read on a phone, archived in another client) are answered with a refresh of one mailbox instead of a cycle: the Inbox, or All Mail on Gmail. With mod-sequences that is a `STATUS` and a `UID FETCH … CHANGEDSINCE` of what changed. Without them (Outlook) the flags of the newest 500 cached copies are read again, about 25 KB, since what a server reports as changed is nearly always recent. The wait then goes on, and the account is never shown as syncing. Refreshes begin at least two seconds apart: the first is immediate, and a burst after it is read together.
  - **Kisa's own changes are reported too.** A server tells the waiting connection about an archive or a mark-as-read made on the foreground one, often before that change has reached the cache. The refresh takes the account's cache lock like a step of a pass, so it waits for the change, finds the cache already right, writes nothing and publishes nothing.
  - **A second mailbox is waited on beside the Inbox,** on a connection of its own, because `IDLE` reports on one mailbox per connection. Where the Inbox is synced (every provider but Gmail) it is Sent, so mail sent from another device shows when it is sent. On Gmail it is All Mail, which sees every arrival and every flag change in the account, where the Inbox sees mail leaving it, in All Mail only a label changing. Mail arriving in that second mailbox is cached in place and starts no cycle: Kisa's own sent copies land there, and on Gmail so does every save of a draft being written on another device. Its refreshes begin at least ten seconds apart, since finding what such a save removed means listing the whole mailbox. The wait lives exactly as long as the Inbox's: it is asked to stop when that one ends, and one that fails, or whose connection the server refuses, ends alone and is tried again at the next wait, so a refused or failing watch connection costs the Inbox's wait nothing. What is not guarded is a server that allows fewer than three connections and accepts this one: with the background and watch connections both waiting, the next foreground connection (opening a conversation, a change) would be the one refused. Mailspring, EmailEngine and the Nylas sync engine wait on All Mail for Gmail too ([research](../research/2026-11-24-imap-push-in-other-clients.md)).
  - **Other mailboxes are not waited on.** That would take a connection each, and `NOTIFY` (RFC 5465), which reports on many mailboxes over one connection, is not used: imapflow has no command for it and no public way to receive its unsolicited `STATUS` responses, and none of Gmail, iCloud or Outlook offers it.
  - **Before each wait,** the server's `UIDNEXT` is compared with the cached one: the Inbox's where the dialect syncs it, All Mail's on Gmail. A pass or a refresh reads the server and the wait begins a moment later; mail that lands in between is reported by neither, so a difference starts a cycle at once. The first wait after such a cycle skips the comparison, so a server whose answers differ on every look gets one cycle and then a real wait.
  - **A wait lasts at most five minutes,** and a cycle runs then whatever happened. That regular cycle reads what `IDLE` on one folder cannot report, which is everything outside the Inbox, and is how a connection that died without a word is replaced. Before `IDLE` this cycle ran every two minutes, so a change in another folder can now take up to five minutes to show while no Kisa window is focused. imapflow ends a quiet `IDLE` after the two-minute socket timeout with a `NOOP` of its own, which keeps the connection alive; Kisa starts the `IDLE` again.
  - **Cycles that new mail starts begin at least five seconds apart,** so a server that reports mail on every wait cannot keep an account syncing.
  - **Ending a wait.** Anything else that asks for a sync ends the wait first, because the cycle needs the same connection: Kisa sends a `NOOP`, which ends the `IDLE`, and gives the server five seconds to answer. One that does not is usually a connection that died while the computer slept; it is dropped and the cycle opens a new one. Quit and disconnect do not ask at all: they drop the connection, so they still never wait on a server that has stopped answering.
  - **Where the server cannot be waited on** (no `IDLE` capability, an Inbox not listed yet, or a wait that failed) the account is polled every two minutes instead. A failed wait is never answered with a cycle at once, so a server that drops every `IDLE` is polled rather than hammered.
  - Tested against a fake server and a stand-in for imapflow's client. Not yet run against Gmail, iCloud or Outlook with these reports. Four things are assumed from the protocol and from other clients, not measured: that each provider sends flag changes to a waiting connection, that Gmail reports on All Mail as it does on the Inbox, that iCloud and Outlook accept a third connection, and that a save of a draft on another device reaches All Mail each time, which is why that wait is paced.
- **Other requests:** the loop also runs at once after a send, after a change that failed, on a label refresh or a "Sync now", when the account is connected again, when a Kisa window gains focus (at most every 30 seconds), and when the computer wakes from sleep. A request that arrives while a cycle is running is remembered and earns one more cycle when it ends. A failed cycle is retried after 5 seconds, 15 seconds, a minute, then every 5 minutes, and any request retries it at once; a delay a throttling server gives is always waited in full. A refused sign-in parks the loop until the account is connected again or the user chooses "Sync now"; focus and the other automatic requests do not retry it.
- **A pass that fails part way:** each step of a pass saves what it read before the next asks the server anything, so a pass that loses its connection after the Inbox has already cached that mail. The next pass finds it cached and reports nothing new, so the failing pass is the only one that can show it. Whatever a pass had saved when it failed is therefore handed over at that moment and published like any other change: the thread list event, the unread badge, notifications and automatic categorization. That covers a failure in a later mailbox and one later in the same mailbox, and the same holds for a refresh during a wait and for the refresh after a change. It is not done when the work is interrupted, as on disconnect or quit, which would announce mail for an account being removed. The retry reports that mail once more as changed at most, never as new.
- **A folder that will not open:** a server can list a folder and refuse its `STATUS` (a shared folder without access, or one deleted since the list was read). A pass leaves such a folder out, logs a warning with its role and no path, and reads the rest, so one folder cannot keep an account from syncing, walking and downloading bodies.
  - **Never the Inbox, nor All Mail on Gmail.** A pass that cannot open the mailbox new mail arrives in fails, as before: an account that looked caught up while receiving nothing would be worse than one that says it is failing.
  - **Only at the opening `STATUS`,** before anything of the folder was read or saved. A folder rebuilt later in its step (another `UIDVALIDITY`) still fails the pass, which the retry starts over.
  - **An answer that leaves out the message count, the next UID or the `UIDVALIDITY` is a refusal too.** Read as an empty mailbox it would let a folder be deleted as empty.
  - **A lost connection is not a refusal.** imapflow answers `false` to a `STATUS` in both cases. The adapter asks whether the connection is still usable: one that is not is a lost connection, which fails the pass and replaces the connection.
  - **No message is deleted for having no copy in such a pass,** since its copy may have moved into the folder that could not be read.
  - **Not handled.** A folder that never opens keeps its account reading as indexing, since its walk never starts, and for the same reason the account's messages without a copy are never cleaned up. A folder that was read before and then refuses for good is left out of each pass, but a skeleton or body step on its cached copies still fails the cycle. Tested against a fake server; no real server has been seen to refuse a listed folder.
- **Changes:** with `CONDSTORE`, and only when a mailbox's `HIGHESTMODSEQ` has moved, a `UID FETCH` of flags (and Gmail labels) with `CHANGEDSINCE` the stored mod-sequence, over the UIDs from the skeleton floor up to the stored `UIDNEXT`. Without `CONDSTORE` (Outlook, and any server that reports no mod-sequence, or a mod-sequence of 0, which RFC 7162 has a server give for a mailbox that keeps none) the background pass re-reads flags instead: each pass, the flags of the newest 500 cached copies of every synced mailbox, plus the next 2,000 below a stored cursor that walks down to the skeleton floor and then starts again. That is at most 2,500 short answers per mailbox per pass, no message content, and covers a 50,000-message mailbox in 25 passes. The cursor is saved in the same transaction as the flags it covers, so an interrupted pass repeats its slice rather than skipping one. Only differences are written: a pass that finds nothing changed writes no message, location or thread row and publishes nothing, and `\Recent`, which a server shows to one connection only, is ignored. The refresh after the user's own change does not re-read.
- **Labels renamed or deleted elsewhere (Gmail):** toggling a label on a message advances `HIGHESTMODSEQ` ([probe](../research/2026-11-21-gmail-imap-probe.md)), but whether renaming or deleting the label itself does was not measured, so Kisa does not rely on it. When the label list loses labels, discovery takes them off cached copies at once: a label the server no longer lists is on no message, so this follows from the list and needs no read of the messages. When it also gains some, as a rename looks, every synced mailbox with cached copies gets a label cursor at its `UIDNEXT`, and the background cycle reads `FLAGS X-GM-LABELS` again for 2,000 cached copies a step, newest first, ahead of the skeleton walk, about 151 bytes a message. Both happen before the catalog is saved, so a pass cut short finds the same difference and repeats them. The cursor moves in the same transaction as the labels it covers, another change starts it over, and a `UIDVALIDITY` reset or a mailbox that stops being synced clears it. A label that only appears needs no reread: mail filed under it later advances its mod-sequence.
- **New mail:** UIDs at or above the stored `UIDNEXT`, found with one `UID SEARCH` of that range. The same answer is held against the copies already cached in the range. There are some when an earlier pass cached new mail and was cut short before it saved the mailbox's `UIDNEXT` and count: the stored count does not cover those copies, so one the search no longer returns is removed at once.
- **Deletions:** neither Gmail nor iCloud is assumed to offer `QRESYNC`. The stored count covers the copies below the stored `UIDNEXT`. When a mailbox's message count is lower than the stored count plus new arrivals, `UID SEARCH ALL` is compared with the cached locations of that mailbox, and locations that are gone are removed at once. Messages left without any location are deleted at the end of the pass, after every mailbox has been read, and again when a skeleton walk finishes. That clean-up waits until every skeleton is complete, because until then a missing copy may only be one the walk has not reached. Delete forever is the exception: it deletes exactly the messages it expunged once they have no copy left.
- **`UIDVALIDITY` changes:** the mailbox's locations are dropped and its skeleton restarts. Messages survive if they reappear under the same id.
- **Checking for drift:** a pass applies what the server says changed, so nothing else would notice a copy the cache lost or kept, or a flag it has wrong: the server sees no change to report. Each background pass therefore holds every synced mailbox's cache against two counts that come with the `STATUS` it sends anyway: the copies cached against `MESSAGES`, and the copies cached as unread against `UNSEEN`. Counting the cache took 2 ms for 21,000 copies and 52 ms for 500,000.
  - **When it runs.** Once a mailbox's skeleton is complete and no reread of it is under way, and only in the background pass. The refresh after the user's own change and the refresh that answers an `IDLE` report use the same code without the check, so a repair never runs inside an archive or between two waits.
  - **A difference is acted on only if a second `STATUS` equals the first.** The pass's counts are older than its fetches, so otherwise the difference may be mail that changed meanwhile, and the next pass looks again.
  - **A different number of copies:** `UID SEARCH ALL` once, then cached copies the server lacks are removed and missing ones are fetched, at most 500 a pass. They are old mail the cache lost, so they are not announced as new.
  - **A different number unread,** judged only once the copies agree: the flags, and Gmail's labels, of every cached copy are read again by the label reread above, 2,000 copies a step between the cycle's other work, so the cache lock is never held for a whole mailbox. That covers a Gmail label the cache has wrong as well.
  - **A count that still disagrees after its repair is not compared again until Kisa restarts.** An unread count that is not exact, or a message Kisa cannot identify, would otherwise repair the same mailbox on every pass.
  - **Every repair logs a warning** with the mailbox's role and the four counts, and no path or address. A repair means a sync bug let the cache drift, which a silent fix would hide.
  - Tested against a fake server. Not measured: that each provider's `UNSEEN` is exact, and that asking for it does not slow its `STATUS`.

## Bodies

Bodies are fetched as `BODYSTRUCTURE` and a fixed list of header fields, then the text parts, never the whole source. The structure is planned into the text parts to fetch and the attachment list; of the structure, only the attachment list is stored. When an HTML part has a plain-text alternative, only the HTML is fetched, and search indexes text extracted from it. Text parts get their transfer encoding removed and their charset converted to UTF-8. Attachments stay on the server until the user opens one, and are then fetched by part number, up to 64 MB. Inline images that a message's HTML names with `cid:` are fetched the first time the conversation is opened, within the inline budget (2 MiB an image, 8 MiB a message), and kept in `mail_inline_images`, so later openings show them from the cache. Opening reads the conversation from the cache first, downloading only bodies it lacks and showing the images already kept, and the reply says whether images the cache lacks or marking it read are still owed. The interface shows that at once and, when something is owed, loads the conversation in full, which fetches and keeps the missing images and marks it read; until then the images keep their space without a broken-image icon. An image that could not be fetched is not kept, so the next opening tries again. Showing kept images records the day they were shown, written at most once a day. After its catch-up pass, at most once a day per account, the background cycle deletes the account's images not shown for as long as the user keeps them: 90 days by default, or 30 days, a year, or forever, chosen in Settings. Changing the period clears at the next cycle. SQLite reuses the freed pages, so clearing bounds the database file rather than shrinking it.

Limits applied in main when the structure is planned: depth 16, 500 parts, 5 MB per text part and 8 MB of text per message. A text part over a limit is offered as an attachment. Parts beyond the depth or part limit are left out.

## Changes

A change is applied to the server first, then to the cache, so the cache never shows something the server refused. What the cache then takes is what the server holds, read back, never what the change was meant to do:

- **Flag and Gmail label changes** send the `STORE`, then one `UID FETCH` of `FLAGS` (and `X-GM-LABELS` on Gmail) for the copies it was sent for, per mailbox, and cache that answer. So a change another client made to the same copy at that moment is in the cache too. A copy the answer leaves out has left the mailbox, and the mailbox is re-read to find out which.
- **Moves, copies and expunges** re-read the mailboxes they touched (and All Mail on Gmail).

Each change acts on every cached copy of the conversation's messages. A read-back that fails after the server took the change fails the action like a lost answer does, and the action asks for a sync. With mod-sequences that pass reads the change. Without them (Outlook) a copy below the newest 500 waits until the rolling re-read of flags reaches it.

The read-back costs each change one `UID FETCH` per mailbox, and a second selection of that mailbox: the adapter selects it read-write for the `STORE` and read-only for the `FETCH`.

Not yet run against Gmail, iCloud or Outlook, and newer than the 2026-11-22 run above. Two things are assumed from the protocol, not measured: that a `UID FETCH` straight after a `STORE` on the same connection already shows the change, and that a `LIST` straight after a `DELETE` no longer has the label.

**UIDs and `UIDVALIDITY`.** A UID names a message only under the `UIDVALIDITY` it was read under. A folder deleted and made again elsewhere, or rebuilt by its server, numbers its mail afresh, and until the next pass the cache still holds the old UIDs. Acting on them would star, move or delete other mail, and a body fetched by one would be saved under the wrong message for good. So every session call that takes or returns UIDs also takes the `UIDVALIDITY` they belong to:

- **Where it comes from.** A cached copy carries the one its UID was read under, and changes, body fetches and attachment downloads send that. A pass sends the one from the `STATUS` it has just compared with the cache.
- **Where it is checked.** In the adapter, against the `UIDVALIDITY` the server gave when the mailbox was selected, so the check costs no command. A mailbox selected under another is refused before anything is sent, as a mailbox that is gone (`MailboxMissingError`). imapflow keeps a mailbox selected between commands, so a selection that differs is made once more before the refusal: it may be older than a rebuild the pass has already seen.
- **What follows.** A refused change fails and asks for a sync, like any failed change. A refused background step fails its cycle, which is retried. Opening a conversation or an attachment there shows what is cached, or an error for the attachment, and asks for a sync too. In each case the next pass sees the new `UIDVALIDITY` and starts the mailbox over.

Asking whether a message is in a mailbox at all, as the send path does for its Sent copy, names no UID and takes no `UIDVALIDITY`.

Tested against a stand-in for imapflow's client and against the fake server. Not yet run against Gmail, iCloud or Outlook.

| Change | Gmail | Generic |
| --- | --- | --- |
| Read, unread | `\Seen` on every copy | Same |
| Star | `\Flagged` on every copy | Same |
| Archive, move to Inbox | Remove or add `\Inbox` in `X-GM-LABELS` on the All Mail copy | Move Inbox copies to the Archive folder, or back. A conversation with no copy in Archive (one filed only in a folder or Sent) is refused rather than reported moved |
| User label | Add or remove the label in `X-GM-LABELS` on the All Mail copy | Copy into the folder, never from a copy in Trash or Spam, which would bring a discarded message back. On removal, delete the folder's copy if a live copy remains elsewhere; otherwise move it to Archive |
| Important | `\Important` on the All Mail copy | Not available |
| Trash | Move every copy to `\Trash` | Same, after remembering where each copy was, for the restore to put it back |
| Spam | Move every copy but the user's own to `\Junk`: copies labelled Sent or Draft stay, so a reply never leaves Sent and Not spam never files it in the Inbox. A conversation of only the user's own mail is refused; across a selection, main sets such conversations apart from the cache before each round, so they fail alone and the rest of the round still goes | Same, after remembering where each copy was, for Not spam to put it back |
| Not spam, restore | Move copies out of `\Junk` or `\Trash` into `INBOX`, which Gmail files in All Mail | Copies Trash or Report spam took go back where they were: before moving, either remembers each copy's mailbox and the one it moves them into, and restoring puts each back, one remembered origin per copy, while that mailbox still exists and is not Spam or Trash itself. So a message in the Inbox and a folder returns to both rather than twice to the Inbox, mail that was archived or filed only in a folder returns there, and the user's own copies Trash took return to Sent and Drafts. A message gets back exactly as many copies as the action took of it, out of the mailbox it put them in, those with the highest UIDs, so a copy that was in Trash or Spam before stays there rather than becoming a second copy in the Inbox. Everything else goes into `INBOX`: mail the server filed as spam, mail trashed elsewhere, and every copy of a message with nothing remembered, or none of whose copies is where the action put them any more. The record lives in main's memory, since only Undo reads it seconds later, and holds the 10,000 messages trashed last per account; a new Trash of the same message replaces it, a restore or disconnect clears it, and after a restart, or for a message no longer remembered, a restore falls back to `INBOX` |
| Delete forever | Expunge the copies in `\Junk` or `\Trash`; copies elsewhere stay | Same |

Gmail's restore keeps no record and moves every copy to `INBOX`, the one restore verified against Gmail. With the fake server, which keeps `\Sent` on a message in Trash as Gmail is expected to, a trashed conversation of only sent mail comes back with the Inbox label too; restoring a sent message anywhere else has not been tried against Gmail.

"A live copy" excludes copies in Trash and Spam, and the mailboxes holding the other copies are re-read before the decision. A label the account does not have, or a system label that cannot be set, is refused rather than ignored.

**Labels.** Names nest with `/`. The server path uses the account's own hierarchy separator, and a name is refused if it starts with a system mailbox name, has an empty segment or control characters, contains a separator other than `/`, or already exists. Every operation resolves the server path from the cached mailbox list, never from the renderer.

- **Create** makes the mailbox. A generic folder is read straight away, so mail filed into it at once is picked up.
- **Rename** renames the mailbox on the server. The cache then moves the mailbox, those under it, their copies, their label ids and their colours to the new names, so colours are kept and nothing is walked again. That move is by rule, so the server is read to confirm it. A generic folder gets a `STATUS` where it is now, as any refresh does: a new `UIDVALIDITY` has it walked again, and mail that reached it meanwhile is cached. On Gmail the relabelled messages are not reported as changed, so every synced mailbox with cached copies gets a label cursor, as for a rename seen elsewhere, and the background cycle reads their labels again. The cursor is set before the cache moves, so a rename cut short after that still has its labels read.
- **Delete** on Gmail deletes the label on the server and leaves the mail in All Mail. The cache drops the label when the mailbox list read straight after no longer has it, as it does for a label deleted elsewhere, not because the deletion was asked for. Deleting a generic folder would delete its mail, so everything in it is first moved to Archive with a server-side search. The folder is deleted only if it is then empty.

**Ordering.** Background sync and foreground changes take turns per account on an account-wide lock, so a sync that read the server before a change cannot undo what the change cached. Foreground work runs under the account's work supervisor: disconnecting cancels it and waits for it before the account's mail is deleted. A change that fails part way asks for a sync, so the cache returns to what the server has. What its refreshes had cached by then is published at once, as for a pass that fails part way (see [Staying current](#staying-current)).

**Reporting a change.** The interface shows a change before the server has it and stops once the action answers, trusting the thread list event from then on (see [Desktop](desktop.md#optimistic-thread-actions)). An event carries at most 200 upserts, so the conversations the user acted on come first in it, ahead of newer ones the change's refresh happened to find; without that, a change that also found new mail could leave its own conversation out, and the interface would show it snap back.

**Bulk.** A selection is grouped by account and changed in rounds of 200 conversations, as many as one event carries, so every conversation of a round reaches the interface changed. The reply lists the conversations that failed so the interface can restore them.

## Sending

SMTP with the account's app password, through nodemailer's `SMTPConnection`: one connection per message, logging off, and `[127.0.0.1]` as the EHLO name so the computer's name stays private.

**The message.** Kisa composes it itself. Header text is stripped of line breaks and encoded (RFC 2047 words of at most 64 characters, RFC 2231 file names). Base64 is folded at 76 characters. Media types and content ids from a forwarded message are checked before they reach a header. `In-Reply-To` and `References` come only from parsed message ids in the cache: the root, the parent's `In-Reply-To`, and the parent. Gmail's skeleton does not fetch `References`, so a Gmail reply carries the parent and grandparent only; that shortened chain is valid and still threads. A forward fetches the original's attachments from the server and keeps the thread headers.

**Bcc.** The envelope lists every recipient. The transmitted message has no `Bcc` header. The copy filed in Sent keeps it, so the sender can see whom they Bcc'd. Gmail files what its SMTP server received, so a Gmail Sent copy shows no Bcc.

**Outcomes.** The server's reply decides: 5xx means refused, 4xx means try later. A failure without a reply means nothing was sent if it came before the message was handed over, and an unknown outcome if it came after. The hand-over is the moment the connection starts reading the message, which happens only after the server accepts `DATA`. The send itself is uninterruptible, bounded by socket timeouts.

| Failure | Meaning | Scheduled send |
| --- | --- | --- |
| `MailAuthError` | Sign-in refused | Needs the user |
| `MailConnectionError`, `MailThrottledError` | Not sent; try again | Retried with backoff |
| `MailSendRejectedError` | Refused | Needs the user |
| `MailProtocolError` | The message or an address is invalid | Needs the user |
| `MailSendUnknownError` | May have been delivered | Looked for in sent mail, then the user decides |

A server may accept a message while refusing some recipients. That is a send: the reply lists the refused addresses, and the composer warns instead of reporting a failure that would invite a second send. Scheduled sends do not yet report refused recipients.

**Sent copy.** Gmail and Outlook file sent mail themselves. For iCloud and other IMAP servers, Kisa searches Sent for the Message-ID and appends a copy with `\Seen` only if none is there, so a retry never leaves two. Outlook files its copy a moment after accepting the message, under a Message-ID of its own: tried on Outlook.com, appending left two copies, since no search for Kisa's Message-ID could find Outlook's. So Kisa adds none, and refreshes Sent 3 and 15 seconds after the send, as MailCraft does for its Graph and Exchange accounts, so the copy shows without waiting for the next sync. That refresh runs as the account's supervised work: the send replies at once, and disconnecting or quitting cancels it. Which rule a provider gets is one table, `SENT_COPY_FILER` in `mail-send.ts`. A failure here never fails the send.

**Finding a sent message.** A scheduled send keeps one Message-ID across attempts. After an unknown outcome, Kisa searches All Mail with `rfc822msgid:` on Gmail, or Sent with a `Message-ID` header search elsewhere. Not finding it does not prove it was not sent (outside Gmail, the Sent copy could have failed after SMTP accepted the message), so the worker asks the user rather than sending again. That Gmail's SMTP server keeps the client's Message-ID has not been verified with a real send yet.

## New mail

When the store caches a message for the first time it reports the message as arrived. Only the incremental part of a sync passes arrivals on: the skeleton walk caches old mail, and a known message moving between mailboxes was not new. After each background pass, after a change whose refresh found new mail first, and for the arrivals a pass, refresh or change had saved when it failed, the engine:

- shows notifications for arrivals that are unread and in the Inbox (see [notifications](notifications.md));
- hands conversations that began with an Inbox arrival to automatic categorization, when the account has it on, which fetches their bodies first because the model reads them.

Every thread-list update also closes notifications for conversations that are no longer unread in the Inbox.

## Search

Search reads only the local cache: FTS over subject, sender address and body text, plus `from:`, `to:`, `subject:`, `is:`, `label:` and `has:attachment` filters answered from cached columns. `is:starred` and `label:starred` match the `STARRED` system id, never a user label of that name, and `label:starred`, the Starred place's scope, leaves Spam and Trash out as the place does. The search bar takes `is:starred` as typed; `is:unread`, `is:read` and `label:` stay free text there, since the Unread toggle and the places own them, and reach main only as the view's scope. Mail whose body has not downloaded is found by its subject, sender and other metadata only. Planned: for mail without a cached body, search the server too (`X-GM-RAW` on Gmail, `SEARCH TEXT` elsewhere) and fetch matching messages that are not cached at foreground priority.

## Security

- Credentials live only in main: each account's app password, or a Microsoft account's refresh token, sealed with `safeStorage` and opened only to sign in a new IMAP or SMTP connection. A Microsoft access token is never stored; it is renewed from the refresh token and kept in memory. How either sign-in happens is described under [Accounts](#accounts).
- Everything a server sends is hostile input. imapflow refuses a literal over 64 MB and a response over 96 MB. Bodies fetch only named header fields, a header block is read up to 1,000 fields, and structure and text are capped as described under [Bodies](#bodies). Those text limits trust the sizes `BODYSTRUCTURE` declares; the bytes actually received are bounded only by imapflow's literal and response caps.
- **Sender authentication is trusted per provider.** Gmail accounts trust only the topmost `Authentication-Results` header, and only when it comes from `mx.google.com`; Gmail adds its header above all others, so a lower one may be the sender's. Other providers report every sender as unauthenticated until their receiving server's header has been verified. Otherwise a sender could forge Google's header in mail sent to an iCloud address.
- No credential, address or message content is written to a log.

## Accounts

An account signs in to IMAP and SMTP with an app password, or, for Outlook.com and Microsoft 365, through Microsoft sign-in. Accounts are rows in `mail_accounts`, keyed by the lowercased address; the sealed credential blob holds the app password or the Microsoft refresh token, tagged with which it is, and is the only place either exists after it is saved.

**Which accounts can connect.** Gmail app passwords require 2-Step Verification. Google does not offer them to accounts whose 2-Step Verification uses only security keys, to work, school or other organization accounts, or to accounts in Advanced Protection ([Google's help](https://support.google.com/accounts/answer/185833)), so those accounts cannot connect to Kisa for now. Some Google Workspace organizations do let their users create one; such an address connects with Gmail's servers, found from its domain (see Server settings below). iCloud accounts use an app-specific password from their Apple Account.

**Where a password is typed.** A dedicated Add account window, opened from the login screen or the Add account button in the sidebar footer. Over the main window it is a modal dialog, a sheet on macOS, and Escape or Cancel closes it; without one it opens as a window of its own. Its first step lists four providers: Gmail, Apple (iCloud Mail), Outlook (Outlook.com, Hotmail and Microsoft 365), and Other. Picking one goes straight to that provider's form, and Back returns to the list with the name and address kept. Gmail and Apple ask for the name, address and app password, Outlook for the name and address, and none of the three shows server settings, looks up a domain, or offers a switch to another way of signing in. Other asks for the name, address, app password and both servers, all at once. Gmail takes any address but another provider's, so a Google Workspace domain sends Gmail's servers without a lookup; Apple takes only `icloud.com`, `me.com` and `mac.com`, the only domains Kisa has checked against Apple's servers, so an iCloud+ custom domain goes through Other; Outlook takes any address but a Gmail or iCloud one; Other takes any address that none of the three claims. An address that belongs to another listed provider is refused in the window, naming the provider to go back to, because main takes a preset address's own servers whatever the window sends. Signing in again skips the list. Either way it is its own `BrowserWindow` with its own HTML entry and preload, sandboxed with context isolation, no Node integration, a `default-src 'none'` policy, no navigation, and no mail content. Its only outside links are the presets' app-password pages (Google's app passwords page and Apple's guide to app-specific passwords) and Microsoft's page on turning IMAP on for Outlook.com, which open in the system browser; it cannot open any other URL. Its preload exposes exactly four calls: submit a password sign-in, start or cancel a Microsoft sign-in, and close. It sends main no domain to look up, so nothing typed into it reaches DNS. The mail window can only ask main to open or focus it, or to open it for a connected account to sign in again; main then reads which account and how it signs in, and tells the page in its URL.

**Name.** The window has an optional Name field: the sender name outgoing mail carries, stored as the account's display name. Blank sends with the bare address. Accounts have no avatar; the sidebar shows the same person icon for every account.

**The one exception to credentials never crossing IPC.** The user has to type the password somewhere the renderer draws, so it crosses IPC once, from the setup window to main, write-only:

- The password input is uncontrolled; React state holds only whether it is empty.
- Main checks the sender is the open setup window and accepts one submission at a time.
- Main decodes the request with an Effect Schema in the handler, not in the IPC runtime, and wraps the password in `Redacted` as it decodes. A malformed request gets one fixed message: a schema issue quotes the value it rejected, and Electron logs a rejected handler.
- Every failure the window sees is fixed text chosen by main. A server's reply is never shown or logged.
- Nothing is returned on success; main closes the window and publishes the updated account list.

**Server settings.** Gmail and Apple use their presets, with the full address as the sign-in name: `imap.gmail.com:993` and `smtp.gmail.com:465`, both over TLS; `imap.mail.me.com:993` over TLS and `smtp.mail.me.com:587` with STARTTLS. Main applies a preset itself for an address on the preset's own domain (`gmail.com` and `googlemail.com`; `icloud.com`, `me.com` and `mac.com`), whatever the window sends, so no network lookup is needed. Under Gmail, any other domain is taken to be Google Workspace on the user's choice: the window sends Gmail's servers with the sign-in, which main checks as it would typed ones. Other shows host, port and security fields for IMAP and SMTP as soon as it opens, starting at 993 with TLS and 587 with STARTTLS; only TLS and STARTTLS are offered, and Microsoft's IMAP server is refused in the window with a pointer to Outlook, since it takes no passwords. Nothing is looked up. Its failures use Gmail's wording, as do those of any account on Google's or Apple's servers, and once its server advertises Gmail's extensions it is stored with provider `gmail`, like a hand-entered Google server. Google shows an app password in groups of four characters, so spaces are removed from the password before signing in to Google's servers.

**Dialect.** Chosen from the IMAP server's capabilities at sign-in, not from the address: `X-GM-EXT-1` gives the Gmail dialect, anything else the generic one (see [Providers](#providers)). A Google Workspace address therefore gets the Gmail dialect, picked as Gmail or entered by hand under Other.

**Verify before saving.** Main refuses an address that is already connected, then signs in over IMAP with the engine's imapflow adapter and lists the mailboxes, refusing a Gmail account that lists no All Mail (see [All Mail hidden from mail apps](#all-mail-hidden-from-mail-apps)), then signs in over SMTP and quits without sending. A refused sign-in says so, and for iCloud says to use an app-specific password rather than the Apple Account password; an unreachable server, a busy server and an unexpected reply each have their own message. Only then is the password sealed with `safeStorage` (Linux `basic_text` refused), the row inserted in a transaction that checks the address again, and the engine started through the account-connected event. Closing the window abandons a verification in progress and nothing is saved, though an IMAP sign-in already under way finishes and logs out first. Once verification has passed, saving and starting the account always run to the end.

**Sign-in at connection time.** Main decrypts the blob for each new IMAP or SMTP connection and hands the connection a `Redacted` password; an unreadable blob is a refused sign-in that asks the user to add the account again. Changing a saved password today means removing the account and adding it again.

**Microsoft sign-in.** Picking Outlook signs any address in with Microsoft, which is how a Microsoft 365 address on its own domain gets there. An Outlook.com, Hotmail, Live or MSN address (told by the first label of its domain, so `hotmail.co.uk` counts) also gets a link to turn IMAP on, and is refused under Other, as Microsoft's IMAP server is. A password sign-in to Microsoft's servers is refused before any server is contacted. The flow is the authorization-code flow for native apps (RFC 8252) with PKCE, and works like this:

- **What the window sends.** Only the address and the optional name. No credential, code or token ever reaches a window.
- **The browser.** Main opens `login.microsoftonline.com/common` in the system browser with the address as `login_hint`, asking for `IMAP.AccessAsUser.All`, `SMTP.Send` and `offline_access`, plus `openid email` to learn who signed in.
- **The redirect.** It returns to a listener bound to `127.0.0.1` on a port the operating system picks, and named `http://localhost:<port>`, the one host whose port Microsoft does not compare with the registration. Only a request carrying the attempt's random `state` counts; other requests are answered and ignored. The listener closes when the sign-in ends: success, refusal, the user's Cancel, closing the window, a ten-minute timeout, or quitting.
- **The check.** The code is exchanged for tokens, the mailbox is opened over IMAP and SMTP accepts the same token, and only then is the refresh token sealed and the account saved. A mailbox that refuses a token Microsoft has just issued usually has IMAP turned off, the default for a new Outlook.com account; if the browser signed in a different account than the one typed, the message says so instead.
- **Signing in again.** Adding an address already connected through Microsoft replaces its sign-in and keeps its cached mail and settings. Add account refuses an address connected with a password; Sign in again, offered in the account's Mail sync row in Settings while its sign-in is refused, opens the same window for that account. It asks only for a new app password, which main checks against the account's stored servers and user name, never against servers the request names, and saves by replacing the sealed password alone, so cached mail and settings stay. A server that now answers as another kind (Gmail or not) is refused, since the cache was built for the old one, and an account disconnected while it was being checked stays disconnected. Each submission from that window must name the account it was opened for.
- **Renewal.** A connection asks for an access token: the one in memory if it has more than five minutes left, otherwise one renewed from the refresh token, one renewal at a time per account. The mail scopes are named in every renewal, since without them a personal account's renewed token is refused for SMTP. Microsoft replaces the refresh token with each renewal; the new one is written over the old with an update only, so an account removed meanwhile does not come back. A token a server refuses is dropped and renewed once.
- **Failures.** Microsoft refusing a renewal asks the user to sign in again. Microsoft being busy, throttling or unreachable is a lost connection that is tried again later, never a sign-out.
- **The client.** Microsoft issues tokens only to a registered app: Kisa's public-client registration in Microsoft Entra, for "Any Entra ID Tenant + Personal Microsoft accounts", with the redirect URI `http://localhost` and no secret. Its Application (client) ID is not in the source: the build reads `MAIN_VITE_MICROSOFT_CLIENT_ID` from `apps/desktop/.env.local` or the shell (see `apps/desktop/.env.example`), and the release workflow from the `MICROSOFT_CLIENT_ID` secret of the GitHub `Prod` environment. A build without it does not offer Microsoft sign-in, and an Outlook account already added asks to sign in again.

Work and school accounts are best-effort: an organization may require an administrator's consent or a verified publisher before users can sign in, and may have SMTP client submission turned off.

**Disconnect.** Main cancels the account's work and waits for it, closes its connections, then deletes the account's sealed sign-in, its access token in memory, cached mail, index rows, progress, settings and sender trust. Nothing is revoked at the provider; a user who wants the app password, or Kisa's access to a Microsoft account, to stop working revokes it in their provider's account settings.

## Interface contract

The mail renderer and its IPC schemas stay as they are. The IPC layer maps the engine's tables to the existing `Gmail*` DTOs, keeping the system label strings the renderer tests for. Renaming those DTOs is cosmetic and comes last.

Account methods are provider-neutral: `listAccounts`, `onAccountsChanged`, `reorderAccounts`, `disconnectAccount` and `openAccountSignIn`, declared in `shared/ipc/accounts.ts` on `desktop:accounts:*` channels. Adding an account belongs to the Add account window's own bridge, described under [Accounts](#accounts).

## Slices

1. **Read-only Gmail:** schema, IMAP transport, Gmail dialect, skeleton and bodies, list, open thread, local search. Done.
2. **Read-only iCloud:** generic dialect and local threading. Done, and verified read-only against a real iCloud mailbox.
3. **Changes:** read state, star, labels and folders, archive, spam, trash, delete forever, label create, rename and delete. Done; verified on Gmail except spam and delete forever, and not yet on iCloud.
4. **Sending:** SMTP, replies, forwards, scheduled mail. Done; new mail and replies verified on Gmail.
5. **New mail:** notifications and automatic categorization from arrivals. Done.
6. **Accounts:** app-password sign-in in a dedicated setup window, with the dialect chosen from the server's capabilities. Done, and verified in the app with a real Gmail account.
7. **Outlook:** Microsoft sign-in, token renewal, and the engine's handling of a server without `CONDSTORE` or `SPECIAL-USE`. Done and tested with fakes and a local token endpoint; not yet run against Microsoft, which needs Kisa's registration. Signed in to a real Outlook.com account: its Sent copy carries a Message-ID of Outlook's own, so a scheduled send whose outcome was unknown cannot be confirmed on Outlook and asks the user to check Sent instead. Still open: whether Exchange sends role attributes in `LIST`, and how fast it answers a 2,500-message flag fetch.
8. **Removal:** the Gmail REST backend, its quota governor, `packages/gmail` and the `gmail_*` tables are gone. The schema is a baseline migration in a new database file, `mail.sqlite` (`mail.dev.sqlite` in development), plus later migrations that drop the account sign-in kind and avatar columns, add the mailbox flag cursor, clear non-Gmail bodies, move message bodies to the end of their rows, and add the sender and unread indexes.
9. **Waiting for news:** `IDLE` on the Inbox between cycles, in place of the two-minute poll, with the poll kept for servers that cannot be waited on. New mail starts a cycle; mail leaving and flags changing refresh one mailbox. A second mailbox (Sent, or All Mail on Gmail) is waited on beside the Inbox. Done and tested with fakes; not yet run against a real server.
